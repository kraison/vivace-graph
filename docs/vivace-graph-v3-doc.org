* Part I: Getting Started

This section will guide you through the fundamental concepts of VivaceGraph. By the end of this part, you will understand what VivaceGraph is, its core design philosophy, and when to use it over other database models.

** Chapter 1: Introduction to VivaceGraph

Welcome to VivaceGraph, a native, high-performance graph database for Common Lisp. This chapter introduces the core features and the architectural philosophy that sets VivaceGraph apart.

*** What is VivaceGraph?

VivaceGraph is a persistent graph database designed from the ground up in Common Lisp. It provides a powerful and expressive environment for modeling, storing, and querying highly connected data.

At its heart, VivaceGraph is built on several key architectural pillars:

  - *Persistent On-Disk Storage (with an in-memory option)*
    By default VivaceGraph stores all data directly on disk using memory-mapped files (see ~mmap.lisp~ and ~allocator.lisp~), so it can handle graphs much larger than system RAM while keeping your data durable between restarts. For graphs that fit in memory — and for mobile/ECL deployments where read latency matters most — an optional *in-memory backend* (~make-memory-graph~) instead keeps the graph as live Lisp objects, trading that scalability for the fastest possible reads. Both share the same schema, transactions, and query surface. See Chapter 15.

  - *An Object-Oriented Lisp Environment*
    Vertices and edges in your graph are not just abstract data containers; they are first-class CLOS (Common Lisp Object System) objects. You define your graph's structure by creating Lisp classes with standard slots, inheritance, and methods (see ~node-class.lisp~).

  - *ACID Transactions*
    All create, update, and delete operations are transactional. VivaceGraph provides a ~with-transaction~ macro that guarantees that a block of operations either completes entirely or is rolled back, ensuring the database remains in a consistent state (see ~transactions.lisp~).

  - *A Declarative Prolog-based Query Language*
    Data is retrieved from the graph using a powerful, Prolog-like query language embedded directly in Lisp. This allows you to express complex graph traversals and pattern-matching queries in a clean, declarative style (see ~prologc.lisp~ and the ~select~ macro).

  - *High-Performance Indexing via Views*
    For fast lookups on node properties, VivaceGraph uses a concept called "views". A view is a secondary index (a persistent ordered index — a skip list by default, or a B+ tree; see Chapter 3) that you can define on any vertex or edge property, dramatically speeding up queries that don't start with a known node ID (see ~views.lisp~).

  - *Built for Concurrency*
    The database is designed for multi-threaded access, with a fine-grained locking system to manage concurrent reads and writes safely (see ~rw-lock.lisp~).

  - *Replication and Offline-First Sync*
    VivaceGraph offers two replication modes. Classic *master-slave* replication (Chapter 10) streams the whole database to always-connected, read-only replicas for high availability and read scaling. *Peer replication* (Chapter 16) is a bidirectional, offline-first hub-and-spoke mode for intermittently connected fleets — each device syncs only the authorized subset it is cleared to see, and can author changes locally while disconnected.

*** Core Philosophy: Graphs as Lisp Objects

The most important concept to grasp about VivaceGraph is that it is not simply a database with a Lisp driver. /VivaceGraph's data model *is* the Lisp object model./

When you retrieve a node from the database, you are not handed a generic hash map or a list of properties. You are given a fully instantiated Lisp object of the type you defined.

Consider this schema:
#+BEGIN_SRC lisp
  (def-vertex user ()
    ((name :type string)
     (signup-date :type timestamp))
    :my-app)
#+END_SRC

When you fetch a user from the database, you get an instance of the `user` class.
#+BEGIN_SRC lisp
  (let ((a-user (lookup-user "some-user-id...")))
    (type-of a-user))
  ;;=> USER
#+END_SRC

This seamless integration has profound implications:
1.  *No Object-Graph Mapper (OGM) is needed.* There is no "impedance mismatch" between your application's objects and the database's storage model.
2.  *You can define methods directly on your graph nodes.* You can add behavior to your `user` or `photo` classes just like any other Lisp object.
3.  *The full power of CLOS is available.* Multiple inheritance, method combinations, and complex class hierarchies can be used to model your domain.

Your application code interacts with the database as if it were just another part of the Lisp image, while VivaceGraph handles the persistence, transaction management, and indexing behind the scenes.

*** When to Use a Graph Database

Graph databases excel at managing and querying data where the *relationships between entities are as important as the entities themselves*. If your application logic involves traversing connections, finding patterns, or analyzing networks, a graph database is likely the right choice.

Consider using VivaceGraph for:
  - *Social Networks:* Finding friends-of-friends, suggesting connections, analyzing community structures.
  - *Recommendation Engines:* "Users who liked this product also liked...", "Products frequently bought together...".
  - *Fraud Detection:* Identifying rings of fraudulent accounts or transactions that share common addresses, IP numbers, or credit cards.
  - *Knowledge Graphs and Ontologies:* Modeling complex semantic relationships, dependencies, and hierarchies.
  - *Network and IT Operations:* Mapping dependencies between servers, applications, and network devices to analyze the impact of outages.

VivaceGraph is *not* the ideal choice for use cases where data is largely disconnected, such as storing simple lists of items, logging, or managing large binary files.

*** Comparison with Relational and NoSQL Databases

To understand where VivaceGraph fits, it's helpful to compare it to other database paradigms.

**** Vs. Relational Databases (e.g., PostgreSQL, MySQL)
   - *The JOIN Problem:* Relational databases are optimized for storing rows of data in tables. To connect data between tables, they use `JOIN` operations. A simple query like "find the friends of my friends" can require multiple, expensive self-joins on a `users` table. As the depth of the query increases (e.g., friends-of-friends-of-friends), the performance degrades significantly.

     In a graph database, this is a simple traversal. The query starts at a given user node and just follows the `[:FOLLOWS]` edges. The performance depends only on the size of the local neighborhood being explored, not the total number of users in the database. This is called /"index-free adjacency."/

   - *Schema Flexibility:* While VivaceGraph is schema-aware, its object-oriented nature makes evolving the schema much easier. Adding a new property to a `user` vertex is a simple change to the class definition, whereas in SQL it requires an `ALTER TABLE` command, which can be a slow, locking operation on large tables.

**** Vs. Document Databases (e.g., MongoDB)
   - *Focus on Relationships:* Document databases store data in rich, self-contained documents (like JSON). They are excellent for data that has a clear owner and nested structure (e.g., a blog post and its comments). However, they are very poor at representing many-to-many relationships *between* documents. Modeling a "follows" relationship in a document DB is awkward and inefficient, often requiring you to manually maintain lists of IDs.

     VivaceGraph makes these relationships first-class citizens. An edge is a core, indexed entity, making traversals fast and natural.

**** Vs. Key-Value Stores (e.g., Redis)
   - *Data Structure:* Key-value stores are the simplest model, mapping a key to a value. They are incredibly fast for direct lookups but have no understanding of the data's internal structure or its connections to other data. You cannot ask a key-value store to "find all users who follow Alice." You would have to model that logic entirely in your application code.

     VivaceGraph provides a rich query language precisely for answering such questions.

In summary, choose VivaceGraph when the *paths, patterns, and connections* in your data are the primary focus of your application.

** Chapter 2: Quick Start: Your First Graph Application

This chapter is a hands-on tutorial that will walk you through the entire lifecycle of a basic VivaceGraph application. We will build a simple social network where users can write posts and follow each other. By the end, you will know how to model, create, read, update, delete, and query graph data.

*** Installation (Quicklisp)

VivaceGraph is a Common Lisp library that can be loaded via Quicklisp. Assuming you have Quicklisp set up, you can load the system with:

#+BEGIN_SRC lisp
  (ql:quickload :graph-db)
#+END_SRC

**** Supported Lisp implementations

VivaceGraph runs on SBCL (>= 1.045), ECL (>= 21.2.1), Clozure CL (CCL), and
LispWorks. The full test suite passes on SBCL (macOS arm64 and Linux x86_64)
and on ECL (macOS arm64 with ECL 26.5.5 and Linux with ECL 21.2.1). You can run
it yourself with ~(asdf:test-system :graph-db)~ (the suite uses FiveAM).

CCL works on Linux x86_64 but /not/ on Apple-Silicon macOS: the Clozure ARM64
port has been stalled for several years and macOS support for Intel (x86_64)
binaries is nearly gone, so there is no usable CCL on M-series Macs. On Apple
Silicon, use SBCL or ECL.

It's recommended to define a package for your application and `:use` the `:graph-db` package to import its symbols.

#+BEGIN_SRC lisp
  (defpackage #:my-social-app
    (:use #:cl #:graph-db))
  
  (in-package #:my-social-app)
#+END_SRC

*** Defining a Schema (~def-vertex~, ~def-edge~)

Before we can store any data, we must define its structure. Our social application will have two types of nodes (*vertices*) and two types of relationships (*edges*).

- *Vertices:* ~user~ and ~post~.
- *Edges:* An ~authored~ edge from a ~user~ to a ~post~, and a ~follows~ edge from one ~user~ to another.

We define these using the ~def-vertex~ and ~def-edge~ macros. Notice that each definition ends with a keyword (~:social-app~) that names the graph this schema belongs to.

#+BEGIN_SRC lisp
  ;; A 'user' vertex with a unique username.
  (def-vertex user ()
    ((username :type string))
    :social-app)
  
  ;; A 'post' vertex with text content.
  (def-vertex post ()
    ((text :type string)
     (timestamp :type integer))
    :social-app)
  
  ;; A directed 'authored' edge connecting a user to a post.
  (def-edge authored ()
    () ; No extra properties on this edge
    :social-app)
  
  ;; A directed 'follows' edge connecting two users.
  (def-edge follows ()
    ()
    :social-app)
#+END_SRC

These macros automatically generate constructor functions (~make-user~, ~make-post~, etc.) and accessor methods for the slots you define.

**** Persistent, ephemeral and meta slots

A slot is *persistent* by default: its value lives in the node's ~data~ alist and is written to disk with the node. Two slot options change that.

- ~:ephemeral t~ ::
  Per-instance state that is *never written to disk*. The slot becomes an ordinary CLOS slot — read and written with ~slot-value~ as usual, and simply absent from everything the node serializes. Use it for a cache or a derived value you want to hang off a node without paying to store it.

  Give an ephemeral slot an ~:initform~. An unset *persistent* slot reads back as ~nil~ (it resolves through the ~data~ alist), but an unset *ephemeral* slot is an unbound CLOS slot and signals ~unbound-slot~ — standard CLOS behaviour, and a sharp edge if you expect the persistent slot's forgiving ~nil~.

  Ephemeral values do not survive a reopen, are not replicated, and are not visible to another process holding the same graph.

- ~:meta t~ ::
  Engine-managed metadata (id, revision, type-id and friends). Not part of a node's user data. You will rarely declare this yourself.

#+BEGIN_SRC lisp
  (def-vertex sensor ()
    ((serial      :type string)          ; persistent, the default
     (last-report :ephemeral t :initform nil))  ; live only, never stored
    :social-app)
#+END_SRC

*** Connecting to the Database (~make-graph~, ~open-graph~, ~close-graph~)

With our schema defined, we can connect to the database. We will store our graph's files in a directory, for example, ~"/var/tmp/social-app/"~.

The global special variable ~*graph*~ must be bound to the active graph instance. A common pattern is to check if the database exists and either create a new one or open the existing one.

#+BEGIN_SRC lisp
  (defvar *my-graph-path* "/var/tmp/social-app/")
  
  (defun connect-to-database ()
    "Creates a new graph or opens an existing one."
    ;; A graph directory always contains heap.dat once created, so its
    ;; presence is a reliable "does this graph already exist?" check.
    (if (probe-file (merge-pathnames "heap.dat" *my-graph-path*))
        (open-graph :social-app *my-graph-path*)
        (make-graph :social-app *my-graph-path*)))
  
  ;; Bind *graph* to our active database connection.
  (defvar *graph* (connect-to-database))
#+END_SRC

*Important:* You must always close the graph when your application is finished to ensure all data is safely written to disk and file locks are released.

#+BEGIN_SRC lisp
  ;; At the end of your application's lifecycle:
  (close-graph *graph*)
#+END_SRC

*** Basic Operations (CRUD) within a Transaction

All operations that modify the database—Create, Update, and Delete—must occur within a transaction. This is done using the ~with-transaction~ macro, which ensures that all the operations within its body succeed as a single atomic unit.

**** Create

We'll use the ~make-user~, ~make-post~, and ~make-follows~ functions that ~def-vertex~ and ~def-edge~ created for us.

#+BEGIN_SRC lisp
  (with-transaction ()
    (let ((alice (make-user :username "alice"))
          (bob (make-user :username "bob"))
          (carol (make-user :username "carol")))
      
      ;; Alice follows Bob and Carol
      (make-follows :from alice :to bob)
      (make-follows :from alice :to carol)
      
      ;; Bob writes a post
      (let ((bobs-post (make-post :text "Hello, graph world!"
                                  :timestamp (get-universal-time))))
        (make-authored :from bob :to bobs-post))))
#+END_SRC

**** Read

Reading data does not require a transaction. However, to look up a node by one of its properties (like a username), we need an index, which VivaceGraph calls a *view*. Let's create a view to find users by their username.

#+BEGIN_SRC lisp
  ;; Define a view named 'user-by-username' on the 'username' slot of 'user' vertices.
  (def-view user-by-username :lessp (user :social-app)
    (:map
      (lambda (user-node)
        ;; The 'yield' function creates an index entry.
        ;; It takes a key (the username) and an optional value.
        (yield (username user-node) nil))))

  ;; Now we can write a helper function to perform the lookup.
  (defun find-user-by-username (name)
    (let ((result (invoke-graph-view 'user 'user-by-username :key name)))
      (when result
        (lookup-vertex (cdr (assoc :id (first result)))))))

  ;; Let's test it:
  (let ((bob (find-user-by-username "bob")))
    (format t "Found user: ~a~%" (username bob)))
#+END_SRC

**** Update

To update a node, you must follow a three-step "copy-on-write" process inside a transaction:
1.  *Copy* the node you want to change using the ~copy~ function.
2.  *Modify* the slots of the new copy.
3.  *Save* the copy back to the database using the ~save~ function.

Let's say Alice wants to write her first post. We find her, create a post, and author it.

#+BEGIN_SRC lisp
  (with-transaction ()
    (let ((alice (find-user-by-username "alice")))
      ;; Alice has no posts yet, let's add one.
      (let ((alices-post (make-post :text "My first post!"
                                    :timestamp (get-universal-time))))
        (make-authored :from alice :to alices-post))))
#+END_SRC

Now, let's say Alice wants to *edit* that post.

#+BEGIN_SRC lisp
  (with-transaction ()
    ;; We'll assume we have a function to get Alice's first post.
    (let* ((alices-post (first (outgoing-edges (find-user-by-username "alice") :edge-type 'authored)))
           (post-copy (copy (lookup-vertex (to alices-post))))) ; 1. Copy the post
      
      (setf (text post-copy) "My first post, edited!") ; 2. Modify the copy
      
      (save post-copy))) ; 3. Save it
#+END_SRC

**** Delete

To delete a node, you use ~mark-deleted~ within a transaction. This performs a "soft delete" by setting a flag on the node. The node is no longer returned in queries unless you explicitly ask for deleted nodes.

#+BEGIN_SRC lisp
  (with-transaction ()
    (let ((carol (find-user-by-username "carol")))
      (when carol
        (mark-deleted carol))))
#+END_SRC

*** Writing Your First Query with ~select~

The true power of a graph database lies in querying relationships. Let's ask a classic graph question: *"Who does Alice follow?"*

We use the ~select~ macro, which takes a list of variables to return and a series of Prolog-style goals.

#+BEGIN_SRC lisp
  (let ((alice (find-user-by-username "alice")))
    (declare (special alice)) ; Make the Lisp variable available to the query

    ;; select-flat returns a simple list ("Bob", "Carol")
    ;; instead of a list of lists (("Bob"), ("Carol"))
    (select-flat (?friend-name)
      ;; Goal 1: Import the Lisp variable 'alice' into the query variable '?alice'
      (lisp ?alice alice)

      ;; Goal 2: Find any node '?friend' connected from '?alice' by a 'follows' edge
      (follows ?alice ?friend)

      ;; Goal 3: Get the 'username' slot from the '?friend' node
      (node-slot-value ?friend username ?friend-name)))
#+END_SRC

This query will backtrack through the database, finding all nodes that satisfy the chain of goals, and return a list of their usernames.

You now have the fundamental tools to build a complete application with VivaceGraph!


* Part II: Core Concepts

With the basics of creating and querying a graph covered, we will now dive deeper into the architecture of VivaceGraph. Understanding these core concepts is essential for optimizing performance, managing storage, and appreciating the design decisions behind the library.

** Chapter 3: The Storage Engine

VivaceGraph is not a monolithic black box. It is a collection of carefully designed components that work together to provide a persistent, high-performance database. At the lowest level is the storage engine, which is responsible for how data is physically laid out on disk.

The root of a VivaceGraph database is a directory you specify. Inside this directory, you will find several files and subdirectories, each with a specific purpose. For example, a graph created at ~"/var/tmp/my-app/"~ might look like this:

#+BEGIN_EXAMPLE
/var/tmp/my-app/
├── .dirty
├── config.dat
├── heap.dat
├── indexes.dat
├── schema.dat
├── edge/
│   ├── config.dat
│   ├── table.dat
│   └── overflow.dat
└── vertex/
    ├── config.dat
    ├── table.dat
    └── overflow.dat
#+END_EXAMPLE

This chapter will explain the roles of these key files.

*** On-Disk Format: Memory-Mapped Files

The foundational technology for VivaceGraph's storage is the use of memory-mapped files, implemented in ~mmap.lisp~.

A memory-mapped file (or 'mmap') is a feature of modern operating systems that allows a program to treat a file on disk as if it were a large array directly in the computer's memory (RAM). Instead of issuing explicit ~read()~ or ~write()~ system calls, you can simply access or modify bytes at a specific offset in this virtual memory region.

This approach provides two critical advantages:

1.  *Performance:* The operating system's kernel is responsible for managing the page cache, which keeps recently used parts of the file in physical RAM. Accessing data that is already in the page cache is nearly as fast as accessing main memory, eliminating much of the I/O overhead associated with traditional database architectures. When a part of the file is needed that isn't in RAM, the OS seamlessly pages it in from the disk.

2.  *Large Data Sets:* Because the entire file is mapped into virtual memory, the database can be much larger than the physical RAM available. VivaceGraph can work with a 100 GB graph on a machine with only 16 GB of RAM, as the OS will efficiently move the necessary data pages between disk and memory as they are requested.

The ~mmap.lisp~ file provides low-level primitives like ~get-byte~, ~set-byte~, and ~serialize-uint64~ that operate on these memory-mapped files. All higher-level data structures in VivaceGraph are built upon these primitives. The ~extend-mapped-file~ function allows these database files to grow dynamically as more data is added.

*** The Heap (~allocator.lisp~): How object data is stored

While a node's core metadata (like its ID and type) is stored elsewhere, the actual user-defined data—the values in the slots of your ~user~ or ~post~ objects—resides in a dedicated memory region called the *heap*, managed by the code in ~allocator.lisp~.

This is not the Lisp runtime's heap; it is a separate, persistent heap implemented inside the ~heap.dat~ file. Its role is analogous to the ~malloc()~ and ~free()~ functions in C.

- *Allocation:* When you save a node with data, VivaceGraph first serializes your Lisp data (e.g., the string `"alice"`) into a byte vector. It then calls the `allocate` function, which finds a block of space in ~heap.dat~ large enough to hold these bytes. The function returns a 64-bit integer representing the offset (the "pointer") to this block. This pointer is then stored as part of the node's core metadata.

- *The Free List:* VivaceGraph employs an efficient memory management strategy. When a node is updated, its old data in the heap is not immediately erased. Instead, the block is marked as "free" and added to a *free list*. This is a hash table that maps block sizes to a list of available blocks of that size.

- *Re-use:* The next time the `allocate` function is called for a new piece of data, it first checks the free list (in `maybe-allocate-from-free-list`) to see if an appropriately sized, reusable block is available. This recycling of space minimizes file growth and prevents fragmentation, which is critical for long-term performance. If no suitable block is found, the heap is extended.

*** The Primary Tables (~linear-hash.lisp~): How nodes are indexed by ID

Given a node's 16-byte UUID, how does VivaceGraph quickly find its core metadata (like its type, revision number, and the data-pointer into the heap)? The answer is a persistent, on-disk hash table. VivaceGraph uses a classic data structure called a *Linear Hash Table* for this purpose, implemented in ~linear-hash.lisp~.

Separate linear hash tables are maintained for vertices and edges, each residing in their own subdirectories (~vertex/~ and ~edge/~).

A linear hash table is designed for graceful, incremental growth, which is essential for a database that must expand without long pauses.
- *Buckets:* The table is composed of on-disk "buckets." A hash function converts a node's UUID into a bucket number.
- *Splitting:* When a bucket overflows with too many entries, the table does not resize all at once. Instead, it maintains a `next-split` pointer. It "splits" the single bucket at this pointer into two, re-distributing its contents. The pointer then advances to the next bucket. This ensures that the work of growing the hash table is spread out over time.
- *Overflow:* If a bucket overflows before it is scheduled to be split, any additional items are placed in a separate ~overflow.dat~ file and chained together.

For these primary node tables, the *key* is the node's 16-byte UUID, and the *value* is a compact, serialized representation of the node's core metadata — its *head*. As of storage format *v2* (the MVCC release) the head is 31 bytes for a vertex (71 for an edge, which appends its ~from~/~to~/~weight~) and is laid out append-only as:

#+BEGIN_EXAMPLE
  flags(1)  type-id(2)  revision(4)  data-pointer(8)  commit-epoch(8)  prev-pointer(8)
#+END_EXAMPLE

The first 15 bytes are byte-for-byte identical to the original (v1) head; ~commit-epoch~ and ~prev-pointer~ were *appended*, which is what makes the v1→v2 migration a simple matter (see Chapter 12, "MVCC: Immutable Versioned Nodes"). ~data-pointer~ is the all-important offset to the node's data in the heap file; ~commit-epoch~ and ~prev-pointer~ drive the versioning machinery described in that chapter. The on-disk storage version is recorded in each memory-mapped region; opening a v1 graph with a v2 build signals an error directing you to ~migrate-graph~.

*** Ordered indexes and pluggable backends (~indexes.dat~)

Beyond the primary UUID→head tables, VivaceGraph maintains *secondary ordered indexes* — the map/reduce *views* (Chapter 8), ~:unique~ *constraints* (Chapter 8), and the *spatial* index (Chapter 13). These all live in the graph's index region (~indexes.dat~) and are built on a single ordered-map abstraction: an on-disk structure that keeps keys in sorted order and supports point lookup, ordered range scans, insert, update and delete.

Two interchangeable *backends* implement that abstraction:

- *Skip list* (~skip-list.lisp~) — the default. A probabilistic ordered structure with O(log n) expected operations and simple, lock-friendly concurrency; range scans walk the bottom-level linked list.
- *B+ tree* (~bplus-tree.lisp~) — a page-oriented alternative (4 KB slotted pages). On disk it beats the skip list on every operation once warm: keys are packed by the page, so a lookup touches far fewer cache lines and disk pages, range scans are sequential within a leaf, and it uses less space. It supports in-place cell edits and merge-on-delete rebalancing.

Both implement the same internal ordered-map protocol, so views, unique indexes and the spatial index are all *backend-agnostic* — the choice is transparent to your application code.

**Choosing a backend.** The backend is a *per-graph* property.

#+BEGIN_SRC lisp
  ;; Global default for graphs that don't specify one (default :skip-list):
  (setf graph-db:*index-backend* :bplus-tree)

  ;; Or per graph, at creation / open time:
  (make-graph :my-app "/var/tmp/my-app/" :index-backend :bplus-tree)
  (open-graph :my-app "/var/tmp/my-app/" :index-backend :bplus-tree)
#+END_SRC

VivaceGraph does *not* read a configuration file for this — set the global ~*index-backend*~ or pass ~:index-backend~ from your own application's configuration. The value is captured in the graph's ~index-backend~ slot (~graph-index-backend~).

**How it is persisted.** Each index records the backend it was written with (views keep a ~:backend~ key in the view metadata; the unique and spatial indexes keep a tag in their on-disk root sidecar). On ~open-graph~, every existing index is reopened with *its own* recorded backend — regardless of the ~:index-backend~ you pass. The ~:index-backend~ argument therefore governs only *new* indexes created afterward. This is exactly what lets one graph safely hold indexes on different backends while you migrate between them.

**Migrating an existing graph from skip lists to B+ trees.** Because the secondary indexes are *derived* from the nodes — they can always be rebuilt from the primary tables — switching backends never touches your data; it only rebuilds the index structures.

The recommended path is an *in-place reindex*: reopen the graph on the new backend and rebuild the three index families, which re-persists each index's backend tag.

#+BEGIN_SRC lisp
  (let ((g (open-graph :my-app "/var/tmp/my-app/" :index-backend :bplus-tree)))
    (regenerate-all-views g)          ; map/reduce views
    (regenerate-unique-indexes g)     ; :unique constraints
    (regenerate-secondary-indexes g)  ; general ordered indexes (:index / def-index)
    (regenerate-spatial-indexes g)    ; spatial indexes
    (close-graph g))                  ; persists the new backend tags
#+END_SRC

Each ~regenerate-*~ / ~rebuild-*~ drops the old on-disk index and rebuilds it by scanning the nodes (via the backend-agnostic ~map-vertices~ / ~map-edges~) on the graph's *current* backend, then persists the new tag; a subsequent plain ~open-graph~ then reopens on B+ trees. Your node data is left in place throughout. (Omit any family your schema doesn't use.)

A logical *snapshot + replay into a fresh graph* also works and rebuilds every index on the target's backend (see Chapter 11, "Backup and Recovery"): snapshot the source, ~make-graph~ the target with ~:index-backend :bplus-tree~, adopt the source schema, and ~replay~. For a pure backend switch the in-place reindex above is simpler — one graph, node data untouched — but snapshot/replay is a sound alternative and the right tool when you also want a clean, defragmented copy.

*** Vector segments (~vseg-*.dat~)

One more derived index lives outside ~indexes.dat~ entirely, because it is not ordered and not a map: the *vector segment* that backs a ~:vector-index~ slot (Chapter 8, "Vector indexes and cosine kNN search"). Each segment is its own memory-mapped file in the graph directory — ~vseg-<owner>-<slot>.dat~, one per indexed slot, named for the *declaring* class that owns it.

The layout is deliberately flat, so that a kNN scan reads one long run of floats:

#+BEGIN_EXAMPLE
  [ header 64 bytes ][ id array: capacity × 16 ][ vector block: capacity × dimension × 4 ]
#+END_EXAMPLE

- *Header* (64 bytes) — magic, format version, ~dimension~, element type (only ~single-float~ today; a foreign value signals rather than being misread), ~capacity~, ~live-count~, the free-list head, and a *clean-shutdown flag*.
- *Id array* — slot /i/ holds the 16-byte node id occupying vector slot /i/. This array is the *authoritative* record of what the segment contains; the id→slot hash used for point lookups is RAM-only and is rebuilt at open by sweeping it. A free cell is marked by all-ones in its first 8 bytes, with the *next* free slot in its second 8 — the free list is threaded through the array itself, costing no extra space. (A freshly created or freshly grown region is free-marked for exactly this reason, so "never written" and "removed" are the same on-disk state.)
- *Vector block* — ~capacity × dimension × 4~ bytes of contiguous little-endian IEEE binary32, slot /i/'s vector at offset /i/ × ~dimension~ × 4. Occupied slots are *not* dense once the free list has been used, so a scan sweeps ~[0, capacity)~ and skips free cells.

*Growth is in-place doubling.* Because the vector block starts after the id array, doubling ~capacity~ moves it: the file is extended, then the existing vectors are relocated to the new block offset high slot first (so the copy never overwrites unread source bytes), and the new id cells are free-marked. The mapping's base address never moves — extension re-maps into the reserved window — so a concurrent reader never faults.

The clean-shutdown flag is what makes recovery cheap: it is cleared (and synced) at open and set again at ~close-graph~. On the next open, a segment that was closed cleanly is reopened and trusted as-is; one that was not is *dropped and rebuilt from the nodes*, since a segment is derived data and always reconstructible.

*** Durability and the Dirty File (~graph.lisp~)

How can VivaceGraph ensure it wasn't terminated abruptly, leaving the database in an inconsistent state? It uses a simple but effective mechanism: the "dirty file."

- *On Startup:* When you call ~make-graph~ or ~open-graph~, a hidden file named ~.dirty~ is created in the root of your database directory.
- *On Shutdown:* When you call ~close-graph~, all files are safely synced to disk, and only then is the ~.dirty~ file deleted.
- *On Next Startup:* When you next call ~open-graph~, it first checks for the existence of the ~.dirty~ file.
  - If the file is *not* present, it means the last session was closed cleanly. The graph opens normally.
  - If the file *is* present, it means the application crashed or was killed before ~close-graph~ could complete. The database is potentially in an inconsistent state, and ~open-graph~ will signal an error, refusing to open and instructing the user to run recovery procedures.

This mechanism prevents the use of a potentially corrupted database, safeguarding your data integrity.

*** An alternative: the in-memory backend

Everything above describes the *on-disk* storage engine, VivaceGraph's default. For graphs that fit in RAM — and especially for mobile/ECL deployments where per-read deserialization is costly — VivaceGraph also ships an *in-memory* backend that holds the graph as live Lisp objects, constructed with ~make-memory-graph~ instead of ~make-graph~. It reuses the same journal for durability (plus a checkpoint image) but replaces the heap and linear-hash tables with in-RAM structures. See Chapter 15.


** Chapter 4: The Object Model

VivaceGraph's most distinctive feature is its deep integration with the Common Lisp Object System (CLOS). Unlike databases that treat data as simple property bags, VivaceGraph models data as a rich hierarchy of Lisp objects. This chapter explores how this object model is structured and how you can leverage it to build powerful, domain-specific applications.

*** The ~node~, ~vertex~, and ~edge~ class hierarchy

At the top of the hierarchy is the ~node~ class, defined in ~clos.lisp~ and ~node-class.lisp~. It is the abstract superclass for anything that can exist in the graph. Every ~node~ instance has a set of core, built-in properties that are essential for the database's internal management:

- ~id~ :: A 16-byte UUID that uniquely identifies the node across the entire database.
- ~revision~ :: An integer that increments with every update, used for optimistic concurrency control.
- ~%deleted-p~ :: A boolean flag indicating whether the node has been marked for deletion.
- ~%data-pointer~ :: A 64-bit integer pointing to the location of the node's serialized data in the heap file.
- ~%type-id~ :: An internal integer representing the node's specific class (e.g., the ID for a `user` vertex).

From ~node~, two fundamental classes inherit: ~vertex~ and ~edge~.

- *~vertex~* (defined in ~vertex.lisp~): Represents the entities or objects in your graph. This is the class you will typically inherit from when defining your own node types like `user`, `product`, or `album`.

- *~edge~* (defined in ~edge.lisp~): Represents the relationships between vertices. In addition to the standard ~node~ slots, an ~edge~ has three more essential properties:
  - ~from~ :: The ID of the vertex where the edge originates.
  - ~to~ :: The ID of the vertex where the edge terminates.
  - ~weight~ :: A floating-point number (defaulting to 1.0) that can be used to assign a cost, strength, or rank to the relationship.

This class structure is the foundation of your graph's schema. When you define a `(def-vertex user (person) ...)` you are creating a new Lisp class named `user` that inherits from `person`, which in turn inherits from `vertex`, and ultimately from `node`.

*** CLOS Metaclass Integration (~node-class.lisp~): How ~def-vertex~ works

How does VivaceGraph intercept standard slot access to read from and write to the database? The answer lies in a powerful feature of CLOS: *metaclasses*.

VivaceGraph defines its own metaclass called ~graph-class~ (in ~clos.lisp~) and ~node-class~ (in ~node-class.lisp~). When you use ~def-vertex~ or ~def-edge~, you are implicitly specifying that your new class should use this custom metaclass instead of the default ~standard-class~.

This special metaclass allows VivaceGraph to customize the fundamental behavior of your objects. Specifically, it overrides the low-level functions that CLOS uses for handling slot operations:

- ~slot-value-using-class~ :: This method is called whenever you try to read a slot's value (e.g., `(name my-user)`). VivaceGraph's specialized version first checks if the node's data has been loaded from the heap. If not, it reads the serialized bytes from disk, deserializes them into a Lisp data structure (an alist), and caches it. It then retrieves the requested value from this data structure. For subsequent accesses, the data is already in memory.

- `(setf slot-value-using-class)` :: This method is called when you try to set a slot's value (e.g., `(setf (name my-user-copy) "new name")`). The specialized version intercepts this call. Instead of just setting a value in a Lisp object in RAM, it updates the internal data alist. Crucially, if this modification happens within a transaction, it flags the node as "dirty" and adds it to the transaction's *write-set*, ensuring the change will be persisted to disk upon commit.

This elegant metaclass architecture is what makes the integration between your Lisp code and the persistent database seamless. You interact with a standard Lisp object, and the metaclass handles the complex machinery of persistence, lazy loading, and transactional state management automatically.

*** Persistent vs. Ephemeral Slots

When you define a class with ~def-vertex~ or ~def-edge~, VivaceGraph makes a distinction between two types of slots, though this is managed implicitly by the framework.

1.  *Persistent Slots:* These are the standard data slots you define in your schema.
    #+BEGIN_SRC lisp
      (def-vertex user ()
        ((username :type string)   ; This is a persistent slot
         (last-login :type integer)) ; This is also a persistent slot
        :my-app)
    #+END_SRC
    The values of these slots are serialized and written to the heap file (`heap.dat`) when a node is saved. They are durable and will be present when the database is reopened in a later session. The metaclass machinery described above is primarily concerned with managing these persistent slots.

2.  *Ephemeral Slots (Internal/Meta):* These are the slots that manage the node's state within the database engine, such as ~id~, ~revision~, ~%deleted-p~, ~%data-pointer~, and — as of the MVCC release — ~commit-epoch~ and ~prev-pointer~ (the version-chain fields described in Chapter 12). Their values are part of the core node metadata (the head) stored in the primary vertex/edge tables, not in the general-purpose heap. They are managed internally by VivaceGraph and are not typically meant for direct modification by application code (with the exception of reading `id` or `revision`).

In the current implementation of VivaceGraph, the distinction is made for you. All slots you define in a ~def-vertex~ call are treated as persistent. All the built-in slots of the base `node`, `vertex`, and `edge` classes are treated as internal meta-slots. This design simplifies schema definition while providing the necessary separation for the database engine to function correctly.


** Chapter 5: Transactions and Concurrency

In any serious database system, it's not enough to simply store data; the system must guarantee that the data remains consistent and correct, even when multiple processes are reading and writing at the same time. This is the role of the transaction and concurrency control systems. VivaceGraph provides a robust, ACID-compliant transactional model to ensure data integrity.

*** The Transaction Manager (~transactions.lisp~)

At the heart of VivaceGraph's consistency model is the *Transaction Manager*. Every graph instance has a single, dedicated `transaction-manager` object, defined in ~transactions.lisp~. You do not need to create this object yourself; it is initialized automatically when you call ~make-graph~ or ~open-graph~.

The transaction manager is the central orchestrator responsible for:

- *Creating and Tracking Transactions:* When you start a new transaction, the manager creates a ~tx~ object to represent that unit of work and tracks its state (~:active~, ~:committing~, ~:committed~, or ~:aborted~).
- *Assigning Transaction IDs:* Once a transaction is ready to be committed, the manager assigns it a unique, monotonically increasing transaction ID. This ID is crucial for the replication system and for validation.
- *Managing the Commit Log:* The manager is responsible for writing committed transactions to the on-disk replication log, ensuring that changes are durable.

Every operation that modifies the graph occurs within the context of the currently active transaction, which is bound to the special variable ~*transaction*~.

*** The ~with-transaction~ Macro

For application developers, the primary interface to the transaction system is the ~with-transaction~ macro. This macro provides the essential guarantee of **atomicity**: all the database operations within its body are treated as a single, indivisible unit. They will either all succeed and be permanently saved, or they will all be discarded as if they never happened.

#+BEGIN_EXAMPLE
  All database writes MUST happen inside a ~with-transaction~ block.
#+END_EXAMPLE

Here is the canonical example of updating a node, which demonstrates the use of the macro:

#+BEGIN_SRC lisp
  (with-transaction ()
    ;; 1. Fetch the original, immutable node from the database.
    (let* ((user (find-user-by-username "alice"))
           ;; 2. Create a mutable copy to work with.
           (user-copy (copy user)))
      
      ;; 3. Modify the copy. This change is tracked by the current transaction.
      (setf (username user-copy) "alice_in_wonderland")
      
      ;; 4. Save the modified copy.
      (save user-copy)))
  ;; <-- At this point, the transaction is automatically committed.
  ;; The change to Alice's username is now durable and visible to all
  ;; other processes.
#+END_SRC

If any error had occurred within the body of the ~with-transaction~ block (e.g., a failed validation, a network error, or a simple Lisp error), the transaction would be automatically *rolled back*. The changes to Alice's username would be discarded, and the database would be left in the state it was in before the transaction began.

*** Read/Write Sets and Validation

How does VivaceGraph handle multiple users trying to modify the database at the same time? It uses a high-concurrency strategy called *Optimistic Concurrency Control* based on read/write set validation.

Every active transaction maintains three sets of objects:

1.  *Read-Set:* A set of all the nodes that have been read *from the main database* during the transaction. When `(find-user-by-username "alice")` is called, the original `alice` node is added to the read-set.
2.  *Create-Set:* A set of all brand-new nodes created within the transaction.
3.  *Write-Set:* A set of all existing nodes that have been modified (via `copy` and `save`) or deleted (`mark-deleted`) within the transaction.

When ~with-transaction~ reaches its end and is ready to commit, it performs a critical *validation* step:

#+BEGIN_QUOTE
  "Has any other transaction committed a change to a node that I read or wrote since I started?"
#+END_QUOTE

Specifically, the transaction manager checks if the current transaction's *write-set* intersects with the *read-set* or *write-set* of any other transaction that has committed since the current one began.

- *Success:* If there are no intersections, the transaction is valid. It is assigned a new transaction ID, and its changes are written permanently to disk.
- *Failure:* If there is an intersection (e.g., another process changed Alice's username right after we read it but before we committed our change), a `validation-conflict` error is signaled. The ~with-transaction~ macro catches this error, rolls back all changes, and *automatically retries the entire block of code from the beginning*.

This optimistic approach avoids taking heavyweight locks during the transaction's execution, allowing for very high read performance. In the rare case of a conflict, the work is simply and safely retried.

*** Locking and Concurrency (~rw-lock.lisp~)

While the transactional system uses an optimistic model for application-level data, the database still relies on low-level locks to protect the integrity of its own internal data structures. VivaceGraph implements a custom, fair *Read-Write Lock*, defined in ~rw-lock.lisp~.

A read-write lock enforces a simple but powerful rule:
- Any number of "readers" can hold the lock simultaneously.
- Only one "writer" can hold the lock exclusively. If a writer holds the lock, no readers can enter.

VivaceGraph uses these locks to protect critical, shared data structures:
- *The Transaction Manager:* A lock ensures that assigning new transaction IDs is a serialized, thread-safe process.
- *Hash Table Buckets:* The buckets of the on-disk linear hash tables are locked during writes to prevent data corruption.
- *View Groups:* When a view is being updated, its parent group is locked to prevent other threads from reading inconsistent index data.

The public API for these locks are the ~with-read-lock~ and ~with-write-lock~ macros. As an application developer, you will rarely, if ever, need to use these locks directly. The transaction system and the view manager handle the necessary locking for you. However, their existence is key to understanding how VivaceGraph guarantees thread safety at the lowest levels of the storage engine.


* Part III: Querying and Indexing

Now that you understand how VivaceGraph stores its data, we'll explore how to retrieve it. This part covers the declarative Prolog query language and the powerful indexing system that makes queries fast and efficient.

** Chapter 6: The Prolog Query Language

At the core of VivaceGraph's data retrieval capabilities is a powerful, embedded Prolog engine. If you're new to Prolog, don't worry. You don't need to be an expert to write effective queries. The core idea is simple: instead of writing procedural code telling the database *how* to find your data, you write declarative rules describing *what* data you are looking for. The engine then uses its powerful pattern-matching and search capabilities to find all possible solutions that fit your description.

*** Introduction to Prolog Concepts (Unification, Backtracking)

To understand VivaceGraph queries, you only need to grasp two fundamental Prolog concepts: unification and backtracking.

**** Variables
In VivaceGraph's Prolog, a variable is any symbol that begins with a question mark, such as ~?user~, ~?post~, or simply ~?x~. Variables are placeholders that the engine will attempt to fill with concrete values as it searches for solutions.

**** Goals
A query is composed of one or more *goals*. A goal is a single parenthesized expression, like `(is-a ?x user)`. The engine's job is to prove that this goal can be true by finding a value for ~?x~ that is, in fact, a user.

**** Unification: The Art of Making Things Equal
The most important concept is *unification*, which is performed by the `=` predicate. Unification is like a powerful form of assignment that works in multiple directions. It's the engine's way of saying, "I will try to make these two things equal."

- *Binding a variable to a value:*
  #+BEGIN_SRC lisp
    (= ?x 10) ; ?x is now bound to the value 10.
  #+END_SRC

- *Binding a variable to another variable:*
  #+BEGIN_SRC lisp
    (= ?x ?y) ; ?x and ?y are now linked. If ?x later becomes "alice",
              ; ?y also becomes "alice".
  #+END_SRC

- *Pattern Matching:*
  #+BEGIN_SRC lisp
    (follows ?user ?friend) ; This is the most common use. The engine will search
                            ; the database for a `follows` edge. If it finds one,
                            ; it will unify ?user with the edge's source node
                            ; and ?friend with the edge's destination node.
  #+END_SRC

**** Backtracking: The Engine's Ability to "Try Again"
This is the magic that allows the engine to find *all* possible solutions to a query. When a goal succeeds, the engine moves to the next goal. If a goal *fails*, the engine doesn't just give up. It *backtracks* to the previous successful goal and asks, "Can you succeed in a *different way*?"

Let's trace a simple query to see this in action: "Find all posts written by Alice."

*Query:*
#+BEGIN_SRC lisp
  (is-a ?user user)
  (node-slot-value ?user username "alice")
  (authored ?user ?post)
#+END_SRC

*Execution Trace:*
1.  *Goal 1:* ~(is-a ?user user)~. The engine finds the first user object in the database. Let's say it's Bob. It unifies ~?user~ with the Bob object.
2.  *Goal 2:* ~(node-slot-value ?user username "alice")~. The engine checks if Bob's username is "alice". It is not. This goal *fails*.
3.  *Backtrack!* The engine goes back to Goal 1 and says, "Give me the *next* user." It finds the Alice object. It unifies ~?user~ with the Alice object.
4.  *Goal 2 again:* ~(node-slot-value ?user username "alice")~. The engine checks if Alice's username is "alice". It is! This goal *succeeds*.
5.  *Goal 3:* ~(authored ?user ?post)~. The engine now searches for all ~authored~ edges starting from the Alice object.
    - It finds the first one, which points to Post #1. It unifies ~?post~ with the Post #1 object. We have found a complete solution: `(?user=Alice, ?post=Post#1)`. The engine reports this solution.
6.  *Backtrack!* The engine asks Goal 3, "Do you have another solution for an edge starting from Alice?"
    - Let's say it finds another, pointing to Post #2. It unifies ~?post~ with the Post #2 object. We have found a second solution: `(?user=Alice, ?post=Post#2)`.
7.  *Backtrack!* The engine asks Goal 3 again. There are no more posts by Alice. Goal 3 now fails.
8.  *Backtrack!* The engine returns to Goal 2, but Goal 2 has no other way to succeed for Alice. It fails.
9.  *Backtrack!* The engine returns to Goal 1. It asks for the next user. There are no more users. Goal 1 fails.

The query is now complete, having found all possible solutions.

*** The ~select~ Macro Family (~select-one~, ~select-flat~)

The primary way you will execute these queries is with the ~select~ macro. Its general form is:
#+BEGIN_SRC lisp
  (select (options) (variables)
    ... goals ...)
#+END_SRC

- ~options~ :: A property list for query options. The most common is ~:flat t~.
- ~variables~ :: A list of the variables whose values you want to be returned in the result.

Let's find the usernames of all users in the database.
#+BEGIN_SRC lisp
  (select () (?name)
    (is-a ?user user)
    (node-slot-value ?user username ?name))
  ;;=> (("alice") ("bob"))
#+END_SRC
By default, ~select~ returns a list of lists, with each inner list containing the values for the variables from one solution.

This is often inconvenient, so we can use the ~:flat t~ option.
#+BEGIN_SRC lisp
  (select (:flat t) (?name)
    (is-a ?user user)
    (node-slot-value ?user username ?name))
  ;;=> ("alice" "bob")
#+END_SRC

Because this is so common, VivaceGraph provides two convenience macros:
- ~select-flat~ is shorthand for `(select (:flat t) ...)`.
- ~select-one~ is for when you only want the *first value* of the *first variable* from the *first solution*. It is extremely useful for lookups where you expect only one result.

#+BEGIN_SRC lisp
  ;; Find the user object for "bob"
  (select-one (?user)
    (is-a ?user user)
    (node-slot-value ?user username "bob"))
  ;;=> #<USER "bob">
#+END_SRC

*** Built-in Predicates

VivaceGraph provides a rich set of built-in predicates to use as goals in your queries. Here are the most important ones.

**** Node and Edge Predicates
| Predicate                                   | Description                                                     |
|---------------------------------------------+-----------------------------------------------------------------|
| ~(is-a ?variable class-name)~               | Succeeds if ~?variable~ is a node of the given ~class-name~.    |
| ~(<edge-name> ?from ?to)~                   | Succeeds if an edge of type ~<edge-name>~ exists.               |
| ~(<edge-name> ?from ?to ?weight)~           | Also unifies ~?weight~ with the edge's weight.                  |
| ~(outgoing-edges ?vertex ?edge-var)~        | Finds all outgoing edges from ~?vertex~.                        |
| ~(incoming-edges ?vertex ?edge-var)~        | Finds all incoming edges.                                       |

*Example:* Find all users who follow Bob.
#+BEGIN_SRC lisp
  (select-flat (?follower)
    (is-a ?bob user)
    (node-slot-value ?bob username "bob")
    (follows ?follower ?bob))
#+END_SRC

**** Slot and Property Predicates
| Predicate                                   | Description                                                     |
|---------------------------------------------+-----------------------------------------------------------------|
| ~(node-slot-value ?node slot-name ?value)~  | Unifies ~?value~ with the value of the node's slot.             |
| ~(weight ?edge ?weight)~                    | Unifies ~?weight~ with the edge's weight (same as the 3-arg version). |

*Example:* Find the text of all posts, along with their timestamp.
#+BEGIN_SRC lisp
  (select () (?text ?time)
    (is-a ?post post)
    (node-slot-value ?post text ?text)
    (node-slot-value ?post timestamp ?time))
#+END_SRC

**** Logic, Control, and Lisp Integration
| Predicate                               | Description                                                              |
|-----------------------------------------+--------------------------------------------------------------------------|
| ~(= ?x ?y)~                             | Unifies ~?x~ and ~?y~.                                                   |
| ~(/= ?x ?y)~                            | Succeeds if ~?x~ and ~?y~ are not equal.                                 |
| ~(> ?x ?y)~, ~(< ?x ?y)~, etc.          | Standard numeric comparisons.                                            |
| ~(lisp ?var lisp-expression)~           | Evaluates the Lisp expression and unifies the result with ~?var~.        |
| ~(or goal1 goal2 ... )~                 | Succeeds if /any/ of the goals succeed.                                  |
| ~(not goal)~                            | Succeeds if the nested ~goal~ fails.                                     |

*Example:* Use the powerful `lisp` predicate to find posts with more than 10 characters.
#+BEGIN_SRC lisp
  (select-flat (?text)
    (is-a ?post post)
    (node-slot-value ?post text ?text)
    (lisp ?length (length ?text))
    (> ?length 10))
#+END_SRC
/Note:/ For the query engine to see Lisp variables used inside a `(lisp ...)` form, they must be declared `special`.

*** Writing Complex Queries with Multiple Goals

The real power of this system comes from chaining goals together to express complex questions. Each goal in the sequence acts as a filter or a generator for the next one.

*Question:* "Find the text of posts written by users that Alice follows."

This is a two-hop traversal: Alice -> Follows -> User -> Authored -> Post.

#+BEGIN_SRC lisp
  ;; Assume (find-user-by-username "alice") is defined as before.
  (let ((alice (find-user-by-username "alice")))
    (declare (special alice))

    (select-flat (?text)
      ;; Goal 1: Start with Alice.
      (lisp ?alice-node alice)

      ;; Goal 2: Find a user that Alice follows.
      ;; The engine finds Bob first. ?friend is unified with the Bob object.
      (follows ?alice-node ?friend)

      ;; Goal 3: Find a post authored by that friend (Bob).
      ;; The engine finds "Hello, graph world!". ?post is unified with that post object.
      (authored ?friend ?post)

      ;; Goal 4: Get the text of that post.
      (node-slot-value ?post text ?text)))
    ;; The engine backtracks on Goal 2, finds Carol, but she has no posts, so Goal 3 fails.
    ;; The final result is ("Hello, graph world!").
#+END_SRC

*** Pattern Matching Graph Structures

The most iconic graph query is finding "friends of a friend." Let's find users who are followed by people Alice follows, but who are not Alice herself and are not already followed by Alice.

This translates to the pattern: `(Alice) -> (friend) -> (friend-of-friend)`.

#+BEGIN_SRC lisp
  (let ((alice (find-user-by-username "alice")))
    (declare (special alice))

    (select-flat (?fof-name)
      ;; Start with Alice
      (lisp ?alice-node alice)

      ;; Find a direct friend
      (follows ?alice-node ?friend)

      ;; Find a friend-of-a-friend (FOAF)
      (follows ?friend ?fof)

      ;; Constraint 1: The FOAF cannot be Alice herself.
      (/= ?fof ?alice-node)

      ;; Constraint 2: The FOAF cannot be someone Alice already follows.
      (not (follows ?alice-node ?fof))

      ;; Get the FOAF's name
      (node-slot-value ?fof username ?fof-name)))
#+END_SRC

This query elegantly expresses a complex set of relationships and constraints. The Prolog engine handles the difficult work of searching, matching, and backtracking to give you exactly the results you described. This declarative power is the primary reason for choosing a graph database, and VivaceGraph provides a uniquely powerful and Lisp-integrated way to harness it.


** Chapter 7: Writing Custom Functors

In the previous chapter, you saw how the `(lisp ...)` predicate provides a powerful escape hatch to run arbitrary Lisp code within a query. While this is excellent for one-off calculations or simple filters, you will often encounter situations where you need to reuse complex logic, improve query readability, or optimize performance-critical operations.

For these cases, VivaceGraph allows you to extend the query language itself by defining your own custom predicates. In Prolog terminology, these are called *functors*. This chapter will show you how to create them and why they are one of the most powerful features of the system.

*** Extending the Query Language with ~def-global-prolog-functor~

A custom functor is essentially a Lisp function with a special signature that the Prolog engine knows how to call. You define one using the ~def-global-prolog-functor~ macro.

The key difference between a normal Lisp function and a Prolog functor is how it signals success. A normal function returns a value. A Prolog functor, when it succeeds, must call a *continuation*—a function passed as its final argument that represents "the rest of the query."

**** Syntax

The basic structure of a custom functor is:

#+BEGIN_SRC lisp
  (def-global-prolog-functor <functor-name>/<arity> (arg1 arg2 ... cont)
    "This is the body of your Lisp function."
    ;; 1. Dereference any Prolog variables to get their Lisp values.
    (let ((val1 (var-deref arg1))
          (val2 (var-deref arg2)))
      ;; 2. Perform your logic.
      (when (your-lisp-condition-is-true val1 val2)
        ;; 3. If the condition is met, call the continuation.
        ;;    This tells the engine the goal has succeeded.
        (funcall cont))))
#+END_SRC

- *`<functor-name>/<arity>`*: The name must follow this convention. For a functor named `my-functor` that takes 2 arguments, you would write `my-functor/2`.
- *`arg1, arg2, ...`*: These are the arguments to your predicate as they appear in a query. They will be Prolog `var` objects.
- *`cont`*: This is the crucial *continuation* argument. It is a function that you *must* call to signal that your goal has succeeded and that the engine should proceed to the next goal in the query. If you do not call `cont`, the engine assumes your goal has failed and will initiate backtracking.
- *`var-deref`*: It is essential to use `var-deref` on your arguments inside the functor to get their actual, bound Lisp values.

**** A Simple Example: `divisible-by/2`

Let's create a simple predicate `(divisible-by ?x ?y)` that succeeds if the number `?x` is evenly divisible by `?y`.

#+BEGIN_SRC lisp
  (def-global-prolog-functor divisible-by/2 (dividend divisor cont)
    ;; Dereference the Prolog variables to get the actual numbers.
    (let ((num-dividend (var-deref dividend))
          (num-divisor (var-deref divisor)))
      ;; Check that both are numbers before proceeding.
      (when (and (numberp num-dividend)
                 (numberp num-divisor))
        ;; Perform the divisibility check.
        (when (zerop (mod num-dividend num-divisor))
          ;; Success! Call the continuation to proceed with the query.
          (funcall cont)))))
#+END_SRC

Now we can use this new predicate directly in any query, just like a built-in one.

*Query:* Find all posts whose timestamp is divisible by 7.
#+BEGIN_SRC lisp
  (select-flat (?text)
    (is-a ?post post)
    (node-slot-value ?post timestamp ?time)
    (node-slot-value ?post text ?text)
    ;; Our new functor in action!
    (divisible-by ?time 7))
#+END_SRC

This is much cleaner and more readable than the equivalent query using the `lisp` predicate:
#+BEGIN_SRC lisp
  (select-flat (?text)
    (is-a ?post post)
    (node-slot-value ?post timestamp ?time)
    (node-slot-value ?post text ?text)
    ;; The less readable way:
    (lisp ?is-divisible (zerop (mod ?time 7)))
    (= ?is-divisible t))
#+END_SRC

*** Use Cases for Custom Functors

Custom functors are the key to building high-performance, domain-specific graph applications. They allow you to encapsulate complex logic and create highly optimized query entry points.

**** Use Case 1: Complex Validation and Business Logic

Imagine your application needs to validate that a string is a valid Social Security Number (SSN). The logic for this is non-trivial and may be used in many different queries. Instead of cluttering your queries with a complex `lisp` call, you can encapsulate it.

Let's assume you have a Lisp function `(ssn-is-valid-p ssn-string)` that returns `t` or `nil`.

#+BEGIN_SRC lisp
  (def-global-prolog-functor valid-ssn/1 (ssn-var cont)
    (let ((ssn-string (var-deref ssn-var)))
      (when (and (stringp ssn-string)
                 (ssn-is-valid-p ssn-string))
        (funcall cont))))

  ;; Now your query is clean and expresses its intent perfectly.
  (select-flat (?user)
    (is-a ?user person)
    (node-slot-value ?user ssn ?ssn)
    (valid-ssn ?ssn))
#+END_SRC

**** Use Case 2: Creating Optimized Query Entry Points (Geospatial)

This is one of the most powerful uses of custom functors: creating a new way to *generate* solutions instead of just filtering them.

Imagine our `user` vertices have a `location` slot storing a `'(latitude longitude)` list. We want to find all users within a 10km radius of a given point. Doing this with `(is-a ?user user)` would require scanning every single user in the database and calculating the distance for each one—this is extremely inefficient.

Instead, we can write a functor that *only* yields users that match the criteria. This is possible because the functor can contain its own loops and logic for finding solutions.

Let's assume we have a helper Lisp function, `(haversine-distance lat1 lon1 lat2 lon2)`, that calculates the distance in kilometers.

#+BEGIN_SRC lisp
  (def-global-prolog-functor users-within-radius/4 (center-lat center-lon radius ?user-var cont)
    ;; This functor will generate solutions rather than just testing them.
    ;; Note that ?user-var starts as an unbound variable.
    
    (let ((c-lat (var-deref center-lat))
          (c-lon (var-deref center-lon))
          (rad (var-deref radius)))
          
      ;; Iterate over all user vertices in the graph.
      ;; (In a real high-performance system, this might query a separate geospatial index
      ;; like an R-Tree, but for this example, we'll iterate).
      (map-vertices
       (lambda (user-node)
         (let ((loc (location user-node))) ; Assumes a slot accessor 'location'
           (when (and loc (listp loc))
             (let ((dist (haversine-distance c-lat c-lon (first loc) (second loc))))
               ;; If the user is within the radius...
               (when (<= dist rad)
                 ;; ...then this is a valid solution.
                 ;; We unify our unbound variable with the user node...
                 (let ((old-trail (fill-pointer *trail*)))
                   (when (unify ?user-var user-node)
                     ;; ...and call the continuation to proceed with this solution.
                     (funcall cont))
                   ;; The engine will backtrack here, so we must undo our binding.
                   (undo-bindings old-trail)))))))
       *graph* :vertex-type 'user)))

  ;; Now, the query to find all users near the Eiffel Tower is trivial and efficient.
  ;; NB: in a query goal you write the predicate name WITHOUT the /arity suffix
  ;; (the compiler appends it from the goal's argument count), just as with the
  ;; built-in predicates above.
  (select-flat (?name)
    (users-within-radius 48.8584 2.2945 10.0 ?user)
    (node-slot-value ?user username ?name))
#+END_SRC

In this advanced pattern, the custom functor acts as an efficient, domain-specific index. It bridges the gap between the declarative query language and the high-performance, procedural code needed to implement custom access paths, giving you the best of both worlds.


** Chapter 8: Indexing (Views, Ordered, Unique and Vector Indexes)

You've seen how to create nodes and query them using the Prolog engine. But what happens when your graph grows to millions of nodes? Searching for a user by their username by iterating through every single user in the database, as we did in the last chapter, will become unacceptably slow.

This is the exact problem that indexes solve in a traditional relational database. VivaceGraph offers four kinds of secondary index, and this chapter covers all of them:

- *Views* (~def-view~) — the most general: an arbitrary ~:map~ function decides what a node contributes, and an optional ~:reduce~ aggregates. Reach for these when the index key is computed rather than simply stored.
- *General ordered indexes* (~:index~ / ~def-index~) — the simplest: index a slot by its value, for equality and range lookups, with no map function to write.
- *Unique constraints* (~:unique~) — an ordered index that additionally *enforces* uniqueness at the commit boundary.
- *Vector indexes* (~:vector-index~) — dense embeddings with cosine kNN search.

If you just want "find the user whose email is X", the general ordered index is what you want, and it is a one-word slot annotation; see "General ordered indexes" below. Views are the more powerful tool for when that is not enough.

*** The "Why": Avoiding Full Graph Scans

Imagine you have a library with millions of books. If you want to find a book by its unique ISBN (its ID), you can go straight to the correct shelf. This is fast and efficient. This is analogous to looking up a VivaceGraph node with ~lookup-vertex~—a direct, indexed operation.

Now, imagine you want to find all books written by "Herman Melville." Without a card catalog sorted by author, your only option is to walk down every aisle, pull every book off the shelf, and check the author's name. This is a *full table scan*, and it's exactly what happens in a database without an index.

A view in VivaceGraph is like creating a new, specialized card catalog for your data. When you define a view on the `username` slot, you are telling VivaceGraph: "Please maintain a separate, sorted list that maps usernames directly to the nodes that contain them."

When you later query for a user by name, VivaceGraph can consult this sorted list (the view's index) to find the answer instantly, without having to scan all the user nodes.

Under the hood, VivaceGraph implements these view indexes as persistent, on-disk *ordered indexes* — a *skip list* (~skip-list.lisp~) by default, or a *B+ tree* (~bplus-tree.lisp~) if the graph selects that backend (see Chapter 3, "Ordered indexes and pluggable backends"). Either provides very fast lookups, insertions, and deletions, making it perfect for maintaining real-time indexes.

*** Defining Map-Only Views (~def-view~ with ~:map~) for Secondary Indexes

The most common use for a view is to create a simple secondary index on a node property. This is done using the ~:map~ part of the ~def-view~ macro. The "map" phase defines how each node is transformed into one or more key-value pairs for the index.

**** Syntax
#+BEGIN_SRC lisp
  (def-view <view-name> <sort-order> (<class-name> <graph-name>)
    (:map
     (lambda (node-instance)
       ;; This lambda is called for every node of type <class-name>
       ;; that is created or updated.
       (yield (key-to-index) (value-to-store)))))
#+END_SRC

- *`<view-name>`*: The name you will use to refer to this index (e.g., `user-by-username`).
- *`<sort-order>`*: Determines how the index is sorted. Use ~:lessp~ for ascending order (A-Z, 0-9) and ~:greaterp~ for descending order.
- *`(<class-name> <graph-name>)`*: Specifies which node type this view applies to.
- *`lambda (node-instance)`*: A function that receives an instance of your node class.
- *`yield (key) (value)`*: The core of the map function. You call `yield` to create an entry in the index.
  - The `key` is the value you want to be able to search for (e.g., a username, an email address, a timestamp).
  - The `value` is typically `nil` for simple indexes, as the index automatically stores the node's ID.

**** Example: Indexing Usernames and Post Timestamps

Let's create two essential indexes for our social application.

1.  An index to find users by their username.
2.  An index to find posts by their creation time.

#+BEGIN_SRC lisp
  ;; From Chapter 2, our schema:
  ;; (def-vertex user () ((username :type string)) :social-app)
  ;; (def-vertex post () ((text :type string) (timestamp :type integer)) :social-app)

  ;; 1. The username index
  (def-view user-by-username :lessp (user :social-app)
    (:map
     (lambda (user-node)
       (when (username user-node)
         (yield (username user-node) nil)))))

  ;; 2. The post timestamp index (sorted newest first)
  (def-view posts-by-time :greaterp (post :social-app)
    (:map
     (lambda (post-node)
       (when (timestamp post-node)
         (yield (timestamp post-node) nil)))))
#+END_SRC

That's it! VivaceGraph will now automatically maintain these indexes. When you create a new user, an entry will be added to the `user-by-username` view. If you update a user's name, the view will be automatically updated to reflect the change.

**** Declarative and Idempotent: Restarts are O(1)

~def-view~ is *declarative and idempotent*, exactly like ~def-vertex~ and ~def-edge~.  You can keep your ~def-view~ forms right next to the ~def-vertex~ forms they index and load them once at application startup; you do not have to guard them or re-run them conditionally.

- *Define before or after the graph is open.*  A ~def-view~ registers the view's specification and reconciles it with the graph.  If the graph is already open (the classic ~make-graph~ → ~def-view~ ordering) it reconciles immediately; if not, ~open-graph~ reconciles every registered view at open time.  So a view may be co-located with its node type and loaded before the graph exists.

- *An unchanged view is never rebuilt.*  The view's on-disk index is persistent and is reopened at open time (~restore-views~).  Re-evaluating an unchanged ~def-view~ form — or simply restarting the application — leaves that index untouched: the restart is O(1), not an O(N) re-scan of every node.  This matters enormously for applications that define all their views on every load.

- *A changed view is rebuilt automatically.*  If you change a view's ~:map~/~:reduce~ code or its sort order, the next reconcile detects the difference, rebuilds the index from scratch, and emits a ~log:warn~.  This is the safe default: serving queries from an index built by an *old* ~:map~ lambda would be a subtle, hard-to-find bug.

- *Forcing a rebuild.*  Use ~regenerate-view~ to force one view, ~regenerate-all-views~ to force all of them, or pass ~:regenerate-views t~ to ~open-graph~ (or ~open-memory-graph~) to rebuild everything at open.

- *Removing a view.*  Deleting a ~def-view~ form does not drop the persisted index (just as deleting a ~def-vertex~ form does not drop the persisted type).  Call ~delete-view~ to remove it explicitly.

These semantics apply uniformly to the on-disk and in-memory backends (see the In-Memory Backend chapter): for a memory-graph the index lives in RAM and is restored from the checkpoint image, but the "unchanged → keep, changed → rebuild" reconcile is identical.

*** Defining Map-Reduce Views for Aggregation

Views can do more than just create simple lookup indexes. They can also perform powerful data aggregations using a *map-reduce* pattern. This is perfect for pre-calculating values like counts, sums, or averages.

The map phase works as before, but the `yield`ed values become the input to the reduce phase.

- *`:reduce`*: You provide a second lambda function that takes two arguments: a list of keys and a list of their corresponding values. Its job is to "reduce" this list of values down to a single aggregate value.

**** Example: Counting Followers

A very common need in a social app is to know how many followers a user has. Calculating this on the fly would require counting all incoming `follows` edges every time, which is inefficient. We can pre-calculate it with a map-reduce view.

Our view will operate on the ~follows~ edge class.

#+BEGIN_SRC lisp
  (def-view follower-count :greaterp (follows :social-app)
    ;; The MAP phase:
    ;; For every 'follows' edge, emit a count of 1 for the user being followed.
    (:map
     (lambda (follows-edge)
       ;; 'to' is the user being followed. We use their ID as the key.
       (yield (string-id (to follows-edge)) 1)))

    ;; The REDUCE phase:
    ;; Take a list of keys and values and return a single aggregated value.
    (:reduce
     (lambda (keys values)
       ;; We are just counting, so we can ignore the keys.
       (declare (ignore keys))
       ;; The values will be a list of 1s, so we just add them up.
       (apply #'+ values))))
#+END_SRC

*How it works:*
1.  When Alice follows Bob, a new `follows` edge is created. The `:map` function is triggered. It yields `("<bob's-id>" 1)`.
2.  When Carol follows Bob, another `follows` edge is created. The map function yields `("<bob's-id>" 1)`.
3.  The reduce function is now invoked for the key `"<bob's-id>"`. It receives `keys` = `("<bob's-id>", "<bob's-id>")` and `values` = `(1, 1)`.
4.  It computes `(apply #'+ '(1 1))`, which returns `2`.
5.  The view stores the final aggregated result: the key `"<bob's-id>"` now maps to the reduced value `2`.

This follower count is now stored directly in the view's index and is updated automatically whenever a user gains or loses a follower.

*** Querying Views with ~invoke-graph-view~ and ~map-reduced-view~

Once your views are defined, you need a way to query them.

**** Querying Map-Only Views

For simple indexes created with only a `:map` function, you use the function ~invoke-graph-view~.

#+BEGIN_SRC lisp
  ;; Usage: (invoke-graph-view 'class-name 'view-name :key <search-key>)

  ;; Find the user with the username "alice"
  (invoke-graph-view 'user 'user-by-username :key "alice")
#+END_SRC

This returns a list of alists, with each alist representing a match:
#+BEGIN_EXAMPLE
  (((:KEY . "alice") (:ID . "uuid-of-alice") (:VALUE)))
#+END_EXAMPLE

You can also use it within a Prolog query with the ~invoke-view~ predicate. This is often more convenient as it performs the unification for you.

#+BEGIN_SRC lisp
  (select-one (?user-object)
    (invoke-view user user-by-username "alice" ?user-object))
  ;;=> #<USER ...>
#+END_SRC

**** Querying Map-Reduce Views

To query the aggregated results of a map-reduce view, you use the function ~map-reduced-view~.

#+BEGIN_SRC lisp
  ;; Let's get Bob's follower count. We need a helper to display the result.
  (defun print-follower-count (user-id _ count)
    (format t "User ~a has ~a followers.~%" user-id count))

  ;; Now, call the function on our view.
  (map-reduced-view #'print-follower-count 'follows 'follower-count)

  ;; If you want the data back as a list instead of printing it:
  (map-reduced-view (lambda (user-id _ count) (list user-id count))
                    'follows 'follower-count
                    :collect-p t)
  ;;=> (("<bob's-id>" 2) ("<carol's-id>" 1))
#+END_SRC

You can also use ~invoke-graph-view~ on a reduce view by passing the `:group-p t` option. This is useful for getting the aggregate value for a *specific* key.

#+BEGIN_SRC lisp
  (invoke-graph-view 'follows 'follower-count :key "<bob's-id>" :group-p t)
  ;;=> ((:KEY . "<bob's-id>") (:ID) (:VALUE . 2))
#+END_SRC

Views are the cornerstone of building high-performance VivaceGraph applications. They provide a flexible and powerful mechanism for both secondary indexing and real-time data aggregation.

*** Unique constraints (~:unique~)

A slot can carry a *uniqueness constraint*: no two live nodes of the same type may share its value. Mark the slot ~:unique~ in ~def-vertex~ / ~def-edge~:

#+BEGIN_SRC lisp
  (def-vertex user ()
    ((username :type string :unique t)                 ; identity uniqueness
     (email    :type string :unique string-downcase))  ; case-insensitive
    :social-app)
#+END_SRC

The value of ~:unique~ is the *uniqueness key* — it says how two values are compared:

- ~t~ or ~equal~ — the value itself (identity).
- ~equalp~ — case/relaxed equality.
- a *canonicalizer* — a symbol, ~#'function~, or ~lambda~ of one argument that maps a value to its canonical form; two values collide when their canonical forms are ~equal~. ~string-downcase~ above makes ~"Bob@x.com"~ and ~"bob@x.com"~ the same email.

Semantics:

- *NULL-exempt* — a node whose unique slot is ~nil~/unbound is unconstrained (many are allowed), matching SQL's treatment of NULL.
- *Cross-subtype* — a constraint declared on a parent type is shared across its subclasses (one index), so a ~user~ and an ~admin~ subclass cannot collide on the same value.
- *Enforced at the commit boundary* — the check runs inside the committing transaction, so a violation aborts the whole transaction cleanly (nothing is written) by signalling ~unique-constraint-violation~. Concurrent commits racing for the same value are serialized, so exactly one wins and the rest are rejected.
- *Durable* — the constraint is backed by a *persistent* unique index (an on-disk ordered index — skip list by default, or a B+ tree; see Chapter 3, "Ordered indexes and pluggable backends" — or the in-RAM map on a memory-graph), reopened with the graph; it is not rebuilt by scanning every node on open.

Handle a violation like any other condition (readers ~ucv-class-name~, ~ucv-slot-name~, ~ucv-value~, ~ucv-existing-id~):

#+BEGIN_SRC lisp
  (handler-case
      (with-transaction () (make-user :username "alice"))
    (unique-constraint-violation (c)
      (format t "~A is already taken by node ~A~%"
              (ucv-value c) (ucv-existing-id c))))
#+END_SRC

**** Scope: uniqueness under peer replication

By default a constraint is ~:scope :local~ — the value is unique within *this* graph. Global uniqueness across a whole fleet is not a coordination-free property, so peer replication (Chapter 16) offers a second scope for VivaceGraph-minted values:

#+BEGIN_SRC lisp
  (def-vertex ticket ()
    ((code :type string :unique t :scope :origin))   ; unique *per authoring device*
    :field-app)
#+END_SRC

~:scope :origin~ *partitions* the constraint by the node's authoring origin: two devices may each mint a ~code~ of ~"A-1"~ without colliding (they are different authors), while a single device may not reuse its own. This is the recommended default for offline-first fleets — it needs no coordination. Devices also maintain the constraint index for *pulled* nodes, so a locally-authored value is checked against everything the device holds, not only what it authored. On a non-peer graph there is a single origin, so ~:origin~ collapses to ~:local~.

Truly global uniqueness — a value that must be unique across *all* devices (~:scope :local~, or a future ~:scope :hub~, in a peer setting) — requires the hub to arbitrate cross-device collisions. That arbiter is not yet built (tracked as issue #51); until then, prefer ~:origin~ for peer-replicated unique values.

*** General ordered indexes (~:index~ / ~def-index~)

A *view* is the most general secondary index — you write a ~:map~ lambda that emits arbitrary keys. When all you want is "index a slot for fast equality and range queries," VivaceGraph offers a lighter, declarative *ordered index* on a slot. It is, in effect, a ~:unique~ index without the enforcement: the same durable, backend-agnostic ordered map (skip list or B+ tree; an in-RAM map on a memory-graph), maintained on the commit path, but a value may be shared by many nodes and nothing is ever rejected.

Declare one in either of two ways. As a *slot option*, symmetric with ~:unique~:

#+BEGIN_SRC lisp
  (def-vertex user ()
    ((username :type string :index t)                 ; ordered index on username
     (email    :type string :index string-downcase)   ; case-insensitive index
     (age      :index t))                              ; numeric range index
    :social-app)
#+END_SRC

or, for a slot you would rather not annotate on the class, with the standalone ~def-index~ (declarative and idempotent like ~def-view~; also the intended home for future composite/multi-slot indexes):

#+BEGIN_SRC lisp
  (def-index user email :social-app :canonicalize string-downcase)
#+END_SRC

Both forms produce the same index; ~def-index~ may even be evaluated before its graph exists (it is reconciled at open, like ~def-view~).

Semantics:

- *Scope* — an index on a class covers that class *and its subclasses* (a subtype IS-A), rooted at the class you name. So an index on ~user.email~ also indexes an ~admin~ subclass; ~(def-index user email …)~ indexes the ~user~ subtree even if ~email~ is declared on a parent.
- *Any slot is indexable* — a declared ~:type~ is *not* required. The type is a *hint*: with it, the index validates values and advertises ordered/range support; without it, the index is equality-first and range scans are meaningful only for homogeneous (mutually comparable) values, exactly the contract untyped slots carry everywhere in VivaceGraph.
- *NULL-exempt* — a node whose indexed slot is ~nil~/unbound is not indexed (like ~:unique~; also keeps the index proportional to nodes that actually have the value). Ordered iteration therefore omits value-less nodes.
- *Collation* — an optional canonicalizer (a 1-arg function: a symbol, ~#'fn~, or a lambda; e.g. ~string-downcase~) transforms the value before keying, for case-insensitive or normalized indexes. A canonicalized index orders by the canonical form, so you get case-insensitive lookup at the cost of original-case ordering from that same index. *Descending* order is a query-time concern (reverse the result), not a separate index.

Query with three functions, each taking the graph explicitly and resolving nodes in *that* graph:

#+BEGIN_SRC lisp
  (index-lookup graph 'user 'email "alice@x.com")     ; => list of matching nodes (equality)
  (index-range  graph 'user 'age :start 18 :end 65)   ; => nodes in [18,65], ascending
  (index-range  graph 'user 'age :start 18)           ; open-ended range
  (map-index (lambda (u) ...) graph 'user 'age)       ; stream every user in age order
#+END_SRC

Querying a *declared* index that happens to hold no matching value returns an empty result; only a slot with no index at all signals an error.

Like views, unique, and spatial, an ordered index is *backend-agnostic* — skip list or B+ tree per the graph's ~:index-backend~ (Chapter 3) — durable on the on-disk backend (reopened from a sidecar, no scan), and rebuilt on open on the memory backend. Devices maintain it for *pulled* nodes too, so a replicated node is findable by index the same as a locally-authored one. Switch a graph's ordered indexes to a different backend in place with ~regenerate-secondary-indexes~ (the parallel of ~regenerate-all-views~; see Chapter 3).

When to reach for which: use a *view* when the index key is computed or you need map-reduce aggregation; use an *ordered index* when you simply want a slot indexed for equality and range. (Two current limitations: multi-slot/composite keys and true reverse-streaming cursors are not yet built but are designed for; and a *lazy* memory-graph does not rebuild its ordered indexes on reopen — see Chapter 3 — so use a non-lazy memory graph if you need them to survive a lazy reopen.)

*** Vector indexes (~:vector-index~) and cosine kNN search

Views, ~:unique~ and ~:index~ all key on values you can *order*. An embedding — the dense float vector an LLM or an image model produces — is not that kind of value: you never ask "which documents have exactly this vector," you ask "which documents are *nearest* this vector." VivaceGraph answers that with a third kind of index, the *vector segment*: a memory-mapped block of fixed-width ~single-float~ vectors, one per node, over which it runs a bounded top-k cosine k-nearest-neighbour search.

Declare it with the ~:vector-index~ slot option, exactly where you would write ~:unique~ or ~:index~:

#+BEGIN_SRC lisp
  (def-vertex document ()
    ((title     :type string)
     (embedding :vector-index t))
    :search-app)
#+END_SRC

That is the whole declaration. Maintenance is automatic and lives on the *transaction apply path*, alongside views, unique constraints and the spatial index — you never call an "add to index" function:

#+BEGIN_SRC lisp
  ;; EMBED is your own function; it must return a (simple-array single-float (*)).
  (with-transaction ()
    (make-document :title "Landmine risk survey"
                   :embedding (embed "Landmine risk survey")))
#+END_SRC

Creating a node stores its vector; updating one overwrites it (and *removes* it if the new value is no longer a conforming vector); deleting a node removes it. The segment is created *lazily*, on the first conforming write, and is sized to that first vector's length.

**** Searching

#+BEGIN_SRC lisp
  ;; (vector-search graph class-name slot-name query-vector k)
  (vector-search *graph* 'document 'embedding (embed "buried ordnance") 10)
  ;;=> ((0.93 . #<16-byte id>) (0.88 . #<16-byte id>) ...)
#+END_SRC

The result is a list of ~(score . node-id)~ conses, best first — a ~single-float~ cosine score in the ~car~ and the node's 16-byte id in the ~cdr~.

*It returns ids, not nodes, and that is the entire point.* A scan touches only the segment's id array and its contiguous block of floats; it never deserializes a node, never touches the heap, never conses one object per candidate. Materialize only the handful you actually want:

#+BEGIN_SRC lisp
  (loop for (score . id) in (vector-search *graph* 'document 'embedding q 10)
        collect (cons score (lookup-vertex id :graph *graph*)))
#+END_SRC

The *ranking contract* is precise and worth relying on:

- *Full cosine*, not a dot product — vectors are *not* assumed to be unit-normalized; whatever you stored is what is scored. Either norm being zero yields a score of ~0.0~ rather than a division error.
- Results are ordered by *score DESCENDING*, and ties are broken by *node id ASCENDING*.
- That tiebreak is applied during collection, not only at the end, so the answer is *deterministic*: the same corpus and the same query give the same k in the same order, whether the segment was built incrementally or rebuilt from scratch.
- ~k~ bounds what is retained, not what is examined: every occupied slot is scored, and only k are kept.

~vector-search~ returns ~nil~ when no segment exists yet. That is deliberately ambiguous — it also covers a misspelled class or slot name, and a slot that carries no ~:vector-index~ declaration at all. If a search comes back unexpectedly empty, check the declaration before you go looking at the data.

**** Ownership: one segment per *declaring* class

This is the detail that trips people up. A segment is keyed by ~(owner-name . slot-name)~, where the owner is the *most general* class in the precedence list that declares the slot ~:vector-index~ — not the node's runtime class. One segment therefore spans the declaring class and *all of its subclasses*, and lives in one file per ~(owner, slot)~ pair.

#+BEGIN_SRC lisp
  (def-vertex document ()  ((embedding :vector-index t)) :search-app)
  (def-vertex report (document) ((author :type string)) :search-app)

  ;; A REPORT's embedding is stored in DOCUMENT's segment, and this search
  ;; resolves to that same segment -- so it returns DOCUMENTs as well as REPORTs.
  (vector-search *graph* 'report 'embedding q 10)
#+END_SRC

This mirrors ~:unique~ and ~:index~ scoping exactly. Searching a subclass does *not* give you a subclass-only result set; if you need one, filter the returned ids by type. Rebuilds follow the same rule, sweeping the owner's whole subtree into the one shared segment.

**** What counts as a vector

A value is indexed only if it is a ~(simple-array single-float (*))~. Anything else — a list, a ~double-float~ array, a general vector, ~nil~, an unbound slot — is *silently ignored* by the index. Nothing is signalled, and the node is simply absent from every search over that slot. This is the one sharp edge in the feature: if your embedding function returns a ~(vector single-float)~ that is not simple, or a double-float array, your corpus will index as empty and look like a bug elsewhere. Coerce at the boundary:

#+BEGIN_SRC lisp
  (defun as-embedding (list-of-numbers)
    (make-array (length list-of-numbers)
                :element-type 'single-float
                :initial-contents (mapcar (lambda (x) (coerce x 'single-float))
                                          list-of-numbers)))
#+END_SRC

*Dimension is fixed by the first vector stored* in a segment and cannot change afterwards. A write whose vector length disagrees is *rejected at the commit boundary* — the check runs inside the committing transaction, before anything durable happens, so the whole transaction aborts cleanly and no node/index drift is possible. A query vector of the wrong length signals for the same reason. Length mismatches are loud; wrong *types* are silent. Only the two behave differently.

**** The lower-level entry points

~vector-search~ is a thin resolver over two exported primitives that take a segment object directly. You reach a segment through the graph's internal ~vector-segments~ table, keyed by the owner cons:

#+BEGIN_SRC lisp
  (let ((seg (gethash (cons 'document 'embedding)
                      (graph-db::vector-segments *graph*))))
    ;; Exactly what vector-search does: bounded top-k over every occupied slot.
    (segment-scan seg q 10)

    ;; Score ONLY a candidate set, exactly, best first.  No k -- the caller
    ;; already chose the candidates -- and the same total order as above.
    (segment-score-subset seg q (list id-a id-b id-c)))
#+END_SRC

~segment-score-subset~ exists as an *extension seam*. It makes no assumption that it has seen every vector in the segment, and ids it does not hold are silently skipped, so an approximate index (ANN, or an int8 pre-rank) can propose a cheap candidate set and have it re-scored *exactly* against the float32 block. Note that it does not de-duplicate: an id offered twice is scored and returned twice.

**** Migrating an existing corpus

Because maintenance is on the apply path, nodes written *before* you added the ~:vector-index~ declaration were never indexed. Fill them in with ~rebuild-vector-segment-batched~, which sweeps live nodes and *adds* what is missing without disturbing what is already there:

#+BEGIN_SRC lisp
  ;; => (values INSERTED SKIPPED)
  (rebuild-vector-segment-batched *graph* 'document 'embedding
                                  :batch-size 5000
                                  :progress-fn (lambda (done seen)
                                                 (format t "~D/~D~%" done seen)))
#+END_SRC

It is *resumable by construction*: the segment itself records which ids it holds, so an interrupted run followed by a clean ~close-graph~ simply leaves a partial segment that the next call finishes. There is no progress file, deliberately — a marker that can disagree with the segment is worse than no marker. ~:batch-size~ is the *cadence* at which ~:progress-fn~ is called (with ~done~ = inserted+skipped and ~seen~ = conforming nodes encountered *in this run*), not a memory buffer; each vector is written as it is met. Over a real corpus this takes minutes, so pass a ~:progress-fn~ — a silent migration looks hung. You may name either the declaring class or any subclass; both resolve to the one owner segment. Serialize migrations of a given segment at the call site — do not run two at once against the same ~(owner, slot)~.

**** Concurrency

Each segment carries its own reader/writer lock. ~segment-scan~, ~segment-score-subset~ and reads take the read side; the apply path's inserts and removals take the write side. Concurrent searches are therefore safe against concurrent commits — including a commit that *grows* the segment — and share the segment freely with each other. Rebuilds are the exception: they run at open, before the graph accepts queries, and are not safe against a live concurrent search.

**** Performance, and the ceiling

Be clear-eyed about what this is: a *brute-force* exact scan over every occupied slot. There is no approximate (ANN) index yet. What you get in exchange is exactness, determinism, and a per-vector cost low enough that brute force carries you a long way.

Measured on SBCL 2.5.5 / macOS arm64 (M3) at dimension 1024, the scan runs at *~1.85 ms per 1000 vectors* while the vector block fits in available page cache — about 190 ms for 100k vectors, sub-second to ~500k.

Past that point it is a *cliff, not a slope*. The vector block is exactly

#+BEGIN_EXAMPLE
  live-count × dimension × 4 bytes
#+END_EXAMPLE

so at dimension 1024 each vector costs 4 KB and one million of them is 4 GB. On an 18 GB laptop, 1M vectors measured *11.3 s* per query against the ~1.9 s a linear extrapolation from 500k predicts — 6x worse, because every query now re-reads the block from disk. Repeated scans did not improve, confirming it is architectural rather than a cold cache.

Use the formula to compute your own ceiling: the cliff sits where ~live × dimension × 4~ crosses the memory the machine can actually keep resident. Its *position* is hardware-dependent; its *shape* is not — performance does not degrade gracefully as you approach it, it falls off. On a large-memory host the constraint becomes CPU instead: at ~1.85 ms/1k, a resident million-vector segment is still roughly 1.9 s per query, which no amount of RAM fixes. That is the point at which an approximate index — proposing candidates for ~segment-score-subset~ to re-score exactly — becomes the answer, and it is the reason that seam exists.

A note on implementations: the hot vector-decode path has an SBCL-specific fast implementation, with a portable fallback used on CCL, ECL and LispWorks. The query layer was developed and tested on SBCL.

** Chapter 10: Replication and High Availability (~replication.lisp~)

For production environments, relying on a single database instance creates a single point of failure. If the machine hosting the database goes down, your application becomes unavailable. To solve this, VivaceGraph provides a built-in *master-slave replication* system, implemented primarily in ~replication.lisp~ and ~transaction-streaming.lisp~.

Replication allows you to maintain one or more read-only copies (slaves) of your primary database (the master). This architecture provides two key benefits:

1.  *High Availability:* If the master instance fails, you can quickly promote one of the slave instances to become the new master, minimizing downtime for your application.
2.  *Read Scaling:* You can distribute read-heavy query workloads across multiple slave instances, reducing the load on the master and improving overall application performance.

*** Architecture: Master-Slave Replication

VivaceGraph's replication model is simple, robust, and asynchronous.

- *The Master:* There is a single *master* graph. This is the only instance where write operations (creates, updates, deletes) are allowed. The master is responsible for accepting new data, committing transactions, and broadcasting those changes to all connected slaves.

- *The Slaves:* You can have one or more *slave* graphs. Slaves connect to the master over a TCP socket and receive a continuous stream of committed transactions. They are strictly read-only from an application perspective; their only source of data modification is the transaction stream from the master.

- *The Transaction Log:* The mechanism that drives replication is the *transaction log*. Every time a transaction is successfully committed on the master, it is serialized into a compact binary format and appended to a log file on the master's disk. This log is a complete, ordered history of every change made to the database.

- *The Streaming Process:* When a slave connects, it tells the master the ID of the last transaction it successfully processed. The master then finds the appropriate transaction log and streams all subsequent transactions to the slave. After the slave is caught up with the historical logs, the master will stream new transactions in real-time as they are committed.

This asynchronous model ensures that write performance on the master is not impacted by slow or disconnected slaves.

*** Setting up a Master and a Slave Graph

Configuring replication involves starting two separate VivaceGraph instances with special options passed to ~make-graph~ or ~open-graph~.

**** 1. Setting up the Master

To configure a graph to act as a master, you must provide two key arguments:
- ~:master-p t~: This flag designates the instance as the master.
- ~:replication-port <port-number>~: The TCP port on which the master will listen for connections from slaves.
- ~:replication-key <secret-string>~: A shared secret password that slaves must provide to connect.

#+BEGIN_SRC lisp
  ;; In the master's Lisp process:
  
  (defvar *master-graph*
    (make-graph :social-app "/var/tmp/master-db/"
                :master-p t
                :replication-port 7878
                :replication-key "a-very-secret-key"))
#+END_SRC

Once started, the master will automatically begin listening on port 7878 for slave connections. You can now perform writes on this master instance as you normally would.

**** 2. Setting up the Slave

To configure a graph to act as a slave, you provide a different set of arguments:
- ~:slave-p t~: This flag designates the instance as a slave.
- ~:master-host <hostname-or-ip>~: The address of the master instance.
- ~:replication-port <port-number>~: The port to connect to on the master.
- ~:replication-key <secret-string>~: The shared secret, which must match the master's key.

#+BEGIN_SRC lisp
  ;; In the slave's Lisp process (could be on a different machine):

  (defvar *slave-graph*
    (make-graph :social-app "/var/tmp/slave-db/"
                :slave-p t
                :master-host "localhost" ; or the master's IP address
                :replication-port 7878
                :replication-key "a-very-secret-key"))
#+END_SRC

Upon startup, the slave will attempt to connect to the master. If successful, it will authenticate and begin receiving a stream of transactions. The slave is now a read-only replica of the master. You can run `select` queries against ~*slave-graph*~, but any attempt to use ~with-transaction~ to modify data will fail.

*** How the Transaction Log is Streamed

The communication protocol between master and slave is designed for efficiency and robustness.

1.  *Handshake:* When the slave first connects, a handshake occurs.
    - The master sends a packet containing its protocol version, graph name, and a checksum (digest) of its schema.
    - The slave verifies that all three of these match its own configuration. If there is a mismatch (e.g., the slave has an older schema), the connection is aborted to prevent data corruption.
    - If the handshake succeeds, the slave sends back an authentication packet containing its `:replication-key` and the ID of the last transaction it successfully stored.

2.  *Catching Up:* The master receives the slave's last known transaction ID. It then uses the function ~applicable-replication-logs~ to find all on-disk transaction log files that contain transactions committed after that point.
    - It begins with the first relevant log file and streams only the necessary transactions (those with a higher ID).
    - It then streams all subsequent log files in their entirety.
    - Each transaction is sent as a self-contained binary packet over the socket.

3.  *Real-Time Replication:* Once the slave is fully caught up with the historical logs, the master keeps the connection open. Whenever a new transaction is committed on the master, the `replicate-transaction` method is called, which immediately broadcasts the serialized transaction packet to all connected slaves.

4.  *Reconnection:* The connection between master and slave can be interrupted at any time (e.g., due to a network partition). The slave is designed to handle this gracefully. Upon detecting a disconnection, it will automatically enter a retry loop, attempting to reconnect to the master with an exponential backoff. Once reconnected, the handshake process starts over, and the slave will request all transactions it missed while it was disconnected, ensuring it eventually regains full consistency with the master.

*** Beyond master-slave: peer replication

Master-slave suits always-connected, read-only replicas that mirror the *whole* master. For an offline-first fleet — intermittently connected devices that each hold only an *authorized subset* of the data and must *author* changes locally — VivaceGraph provides a separate, bidirectional *peer replication* mode built on the same durable change feed. See Chapter 16.


** Chapter 11: Backup and Recovery

A database is only as valuable as the data it holds. Ensuring that you can protect that data from hardware failure, software bugs, or human error is a critical operational requirement. VivaceGraph provides a straightforward yet robust mechanism for creating full backups of your graph and restoring them for disaster recovery or for populating new environments.

*** Using ~snapshot~ and ~backup~

VivaceGraph offers two functions for creating backups, but for most use cases, you should use the high-level ~snapshot~ command.

**** The ~snapshot~ Command: Your Primary Backup Tool

The ~snapshot~ function is the recommended, safe, and consistent way to back up your graph.

#+BEGIN_SRC lisp
  ;; Usage: (snapshot graph &key include-deleted-p check-data-integrity-p)
  
  ;; Create a snapshot of the currently active graph.
  (snapshot *graph*)
#+END_SRC

When you call ~snapshot~, it performs several important steps to ensure a high-quality backup:

1.  *Acquires a Write Lock:* It locks the entire transaction system. This guarantees that no new data is being written to the database while the backup is in progress, ensuring the snapshot represents a single, consistent point in time.

2.  *Checks Data Integrity (Optional but Recommended):* By default, ~snapshot~ first runs a full data integrity check on the graph. It iterates through every vertex and edge, attempting to deserialize its data from the heap. This is an invaluable process that can detect data corruption *before* it gets written into your backup file. If any corruption is found, the snapshot is aborted, and a list of the problematic nodes is returned.

3.  *Writes the Backup File:* It then calls the lower-level ~backup~ function to serialize every node and edge in the graph into a single, human-readable text file. The file is saved in a subdirectory of your graph's location named `txn-log/`, with a timestamped filename like `snap-3979326061.272155.log`.

The resulting file contains a series of Lisp s-expressions, one for each node in the graph. This format is not only easy to inspect but is also crucial for the restore process.

#+BEGIN_EXAMPLE
  ;; A snapshot file looks like this (ids abbreviated):
  (:V USER ((:USERNAME . "alice")) :ID #V((UNSIGNED-BYTE 8) 37 22 12 ...) :REVISION 2 :DELETED-P NIL)
  (:V USER ((:USERNAME . "bob")) :ID #V((UNSIGNED-BYTE 8) 91 4 200 ...) :REVISION 1 :DELETED-P NIL)
  (:E FOLLOWS #V((UNSIGNED-BYTE 8) 91 4 200 ...) #V((UNSIGNED-BYTE 8) 37 22 12 ...) 1.0 NIL :ID ... )
  ;; a vector-valued slot carries its element type too:
  (:V DOC ((:EMBEDDING . #V(SINGLE-FLOAT 1.0 1.25 1.5))) :ID ... :REVISION 0 :DELETED-P NIL)
  ...
#+END_EXAMPLE

**** The ~backup~ Function

The ~backup~ function is the underlying worker called by ~snapshot~. It handles the process of iterating through all nodes and writing their serialized representations to a Lisp stream. While you can call it directly, it does not provide the safety guarantees (locking and integrity checks) of `snapshot`, so its direct use is discouraged for production backups.

*** Restoring a Graph from a Snapshot (~replay~)

The `replay` function is the counterpart to `snapshot`. It reads a snapshot file and uses it to reconstruct a graph from scratch. This is the primary tool for disaster recovery or for cloning an existing graph into a new environment (e.g., for staging or development).

*Important Prerequisite:* The `replay` function must be run on a *new, empty graph*. You cannot replay a snapshot on top of an existing graph with data in it.

The restoration process is as follows:

1.  *Create a new, empty graph* in a different directory.
2.  *Call ~replay~*, passing it the new graph instance and the path to the directory containing your snapshot files.
3.  `replay` will automatically find the *most recent* snapshot file in that directory.
4.  It reads the snapshot file one s-expression at a time and, in small, manageable transactions, recreates each vertex and edge.
5.  *Crucially, after all nodes and edges have been restored, ~replay~ automatically regenerates all defined views.* The snapshot file contains only the raw node data, not the indexes. This final step rebuilds the high-performance view indexes from the restored data, making the new graph ready for querying.

The same "indexes are derived, node data is not" principle covers *vector segments* (Chapter 8): a segment never appears in a snapshot file, and because it is maintained on the transaction apply path, it is repopulated as the restoring transactions recreate the nodes.

#+BEGIN_QUOTE
*Vector-valued slots in the snapshot text (issue #56, fixed).* A snapshot file is Lisp
text, and standard ~#(...)~ syntax throws a vector's element type away — it always reads
back as a ~simple-vector~. graph-db used to paper over that by coercing *every* ~#(...)~
in a snapshot to ~(simple-array (unsigned-byte 8) (*))~, because node ~:ID~ values (and an
edge's ~from~ / ~to~) are byte vectors and the reader could not tell an id from slot data.
That made any non-byte vector slot — a ~single-float~ embedding, say — a hard restore
failure: /The value 1.0 is not of type (UNSIGNED-BYTE 8)/.

The snapshot format now writes the element type down. ~backup~ prints any vector whose
element type is not ~T~ as ~#V(<element-type> e1 e2 ...)~ — for example
~#V(SINGLE-FLOAT 1.0 1.25 1.5)~ or ~#V((UNSIGNED-BYTE 8) 37 22 12)~ — and ~replay~ rebuilds
the array with exactly that element type. Plain ~#(...)~ now reads as an ordinary
~simple-vector~, and strings are untouched. (~*print-readably*~ is deliberately not used:
SBCL's ~#A((3) SINGLE-FLOAT ...)~ is an SBCL extension, and a snapshot taken on one
implementation must restore on SBCL, CCL, ECL and LispWorks alike.) So a graph holding
~:vector-index~ slots now round-trips through ~snapshot~ and ~replay~ with its embeddings
intact, and the segment repopulation described above happens as advertised.

*Compatibility is one-way.* A snapshot written by this version is *not* readable by an
older graph-db, which does not know ~#V~. A snapshot written by an older graph-db *is*
readable by this one: its bare-~#(...)~ ids, and an edge's ~from~ / ~to~, are coerced back
into id byte vectors during the replay. The one thing an old file cannot give back is
the element type of a node's own vector-valued *slots* — that was never recorded — so
such a slot restores as a plain ~simple-vector~; take a fresh snapshot afterwards to
capture the types. The on-disk graph format is unchanged by all of this.
#+END_QUOTE

The same derivation is what makes crash recovery cheap outside of backup entirely — a segment that was not cleanly closed is dropped and rebuilt from the nodes on the next ~open-graph~ (Chapter 3, "Vector segments").

**** Complete Example: Backup and Restore

Here is a complete, end-to-end example.

#+BEGIN_SRC lisp
  ;;;; 1. SETUP: Create and populate an original graph.
  (defvar *original-db-path* "/var/tmp/original-db/")
  (defvar *restored-db-path* "/var/tmp/restored-db/")

  ;; Make sure the directories are clean for the example.
  (uiop:delete-directory-tree *original-db-path* :validate t)
  (uiop:delete-directory-tree *restored-db-path* :validate t)

  ;; Define a simple schema for our original graph.
  (def-vertex person () ((name :type string)) :original-graph)
  (def-view person-by-name :lessp (person :original-graph)
    (:map (lambda (p) (yield (name p) nil))))
  
  (let ((original-graph (make-graph :original-graph *original-db-path*)))
    (let ((*graph* original-graph))
      ;; Add some data.
      (with-transaction ()
        (make-person :name "Alice"))
      
      ;;;; 2. BACKUP: Take a snapshot of the original graph.
      (format t "Taking snapshot of original graph...~%")
      (snapshot original-graph)
      (format t "Snapshot complete.~%")
      
      ;; We are done with the original graph.
      (close-graph original-graph)))


  ;;;; 3. RECOVERY: Restore the snapshot into a new, empty graph.
  
  ;; Create a new, empty graph instance for the restored data.
  ;; Note: The graph name can be different, but the schema definitions must be loaded.
  (let ((restored-graph (make-graph :original-graph *restored-db-path*)))
    (let ((*graph* restored-graph))
      (format t "Replaying snapshot into new graph...~%")
      ;; Replay from the directory where the snapshot was saved.
      (replay restored-graph (merge-pathnames "txn-log/" *original-db-path*)
              :package-name :my-app) ; Specify the package where the schema is defined.
      (format t "Replay complete.~%")
      
      ;;;; 4. VERIFICATION: Check if the data exists in the new graph.
      (let ((result (invoke-graph-view 'person 'person-by-name :key "Alice")))
        (assert result)
        (format t "Successfully found 'Alice' in the restored graph!~%"))
        
      (close-graph restored-graph)))
#+END_SRC

*** Migrating a pre-MVCC graph (~migrate-graph~)

The ~migrate-graph~ function does this for you; it is a logical snapshot-and-replay and is described in Chapter 12, "MVCC: Immutable Versioned Nodes."

** Chapter 12: MVCC — Immutable Versioned Nodes

VivaceGraph took early design inspiration from CouchDB, including its idea of keeping previous revisions of a document around rather than overwriting them in place. The MVCC release makes good on that idea: every update or delete now writes a *new* version of a node and *retains* the old one, chained together, until a background reaper decides it is safe to reclaim. This chapter explains how that works and the knobs you have for controlling it.

The benefits are threefold:

1. *The node-data read-after-free race is dissolved at its source.* Because an updated node's old data block is no longer freed at commit time, a concurrent reader that is mid-way through dereferencing it can never have the ground pulled out from under it. (Earlier versions guarded this with a per-read byte-copy under a bucket lock; that machinery is gone, replaced by lightweight read-epoch pins.)
2. *Transactional reads get snapshot isolation* (for lookups — see the note below).
3. *History is preserved* (bounded by your retention policy), laying the groundwork for future time-travel and audit features.

*** The version chain

Recall from Chapter 3 that a node's *head* gained two fields in storage format v2:

- ~commit-epoch~ :: the id of the transaction that committed this version. Transaction ids are globally monotonic, so this acts as a logical timestamp.
- ~prev-pointer~ :: a heap address pointing at the *previous* version's archived head (0 if there is none).

When you update or delete a node, the engine:

1. Writes the new version's data to the heap as usual.
2. *Archives the prior version's head* into its own small heap block (its ~data-pointer~ still references the now-retained old data block).
3. Sets the new live head's ~prev-pointer~ to that archived block and stamps its ~commit-epoch~ with the committing transaction id.

The result is a singly-linked chain, newest-first: the live head (in the primary lhash table) points back through ~prev-pointer~ to each older version in the heap. The garbage collector (~gc-heap~) is version-aware — it roots these chains — so reopening a graph never reclaims a retained version out from under you.

A crucial property for replication: ~prev-pointer~ is a *local heap address*. It is therefore **never** sent on the replication wire. The shared apply path re-derives it (and ~commit-epoch~) from the slave's own current node, so master and slave each build their own correct local chains. (See Chapter 10.)

*** Controlling retention with ~:keep-revisions~

By default a node keeps *no* extra history: the reaper reclaims a prior version as soon as it is safe to do so (see below), so in steady state you pay only for the single in-flight prior version. You can ask the engine to retain a deeper window with ~:keep-revisions~, available at two levels:

- *Per node-type*, on ~def-vertex~ / ~def-edge~:

#+BEGIN_SRC lisp
  ;; Keep the 5 most recent prior versions of every audited-record.
  (def-vertex audited-record ()
    ((payload :type string))
    :my-app
    :keep-revisions 5)
#+END_SRC

- *Graph-wide default*, on ~make-graph~ (persisted with the schema) and overridable on ~open-graph~:

#+BEGIN_SRC lisp
  (make-graph :my-app "/var/db/my-app/" :keep-revisions 3)
  ;; ... later, open with a different retention policy for this session:
  (open-graph :my-app "/var/db/my-app/" :keep-revisions 10)
#+END_SRC

A node-type's own ~:keep-revisions~ overrides the graph default; ~nil~ on the type means "inherit the graph default." A value of ~0~ means "retain only what active readers require."

*** The reaper: lazy and epoch-gated

Reclamation is *lazy* (it runs as part of each commit) and *epoch-gated* so it can never free a version that an in-progress reader or transaction might still observe. The rule is conservative and simple: a prior version is reclaimable only once its *stop epoch* — the ~commit-epoch~ of the version that superseded it — is strictly older than the oldest epoch any active transaction or pinned reader could be reading at. Concretely, the reaper retains ~max(keep-revisions, what active readers still need)~ for each chain it visits, frees the safe oldest suffix, and repairs exactly one ~prev-pointer~ to close the gap.

You do not call the reaper directly; it is automatic. Its only tunable is the retention window described above.

*** Snapshot-isolation reads

Inside a transaction, a point ~lookup~ (e.g. ~lookup-vertex~, ~lookup-edge~, or a generated ~lookup-<type>~) now returns the version that was live *as of the transaction's start* — the newest version whose ~commit-epoch~ precedes the transaction's start epoch. An update committed by a *later* transaction is therefore invisible to an in-progress one, and re-reading a node within a transaction is repeatable. The relevant older version is guaranteed to still exist because an open transaction holds the reaper's floor down.

#+BEGIN_SRC lisp
  ;; Transaction A reads X, sees its value as of A's start, and keeps seeing
  ;; that value even if a concurrent transaction B commits an update to X.
#+END_SRC

*A note on scans.* This isolation applies to *lookups* (and to *typed* scans such as ~(map-vertices fn g :vertex-type 'user)~, which resolve each node through the lookup path). An *untyped*, whole-graph scan — ~(map-vertices fn g)~ with no ~:vertex-type~ — still reads each node's *live* version. This is a deliberate, documented limitation: making whole-graph scans snapshot-consistent would require versioning the indexes themselves (membership history), which is out of scope. In practice untyped scans are used for read-only maintenance and analytics, where this is harmless; when you need a consistent view, use a point lookup or a typed scan. Crucially, none of this affects *data integrity*: writes remain serializable via the engine's optimistic concurrency control regardless of how reads are resolved.

*** Migrating a v1 graph to v2 (~migrate-graph~)

The MVCC head grew from 15 to 31 bytes, so a v2 build cannot open a v1 graph directly. ~migrate-graph~ brings one across without touching the original:

#+BEGIN_SRC lisp
  ;; Load the schema (def-vertex / def-edge forms) for the graph first, then:
  (let ((g (migrate-graph :my-app
                          "/var/db/my-app-v1/"    ; existing v1 graph (untouched)
                          "/var/db/my-app-v2/"    ; fresh v2 graph to create
                          :package :my-app)))
    ;; g is the new, open v2 graph.
    ...)
#+END_SRC

Internally it is a *logical* snapshot-and-replay, the same format-independent mechanism used for backups: the v1 graph is opened read-only through a 15-byte-head shim, every live node is written to a pointer-free snapshot, and a fresh v2 graph is created and the snapshot replayed through the normal ~make-vertex~ / ~make-edge~ path. The original directory is left byte-for-byte untouched. (This mirrors the migration advice given for the 2016 hashing change — snapshot and replay — now packaged as a single call.)

Note that, because the on-disk format uses ~cl-store~ for some structures, graph *directories* are not portable across Lisp implementations; migrate (and snapshot/replay) on the same implementation that wrote the graph.

** Chapter 13: Spatial Queries

VivaceGraph ships a general-purpose *spatial extension*: a geohash-backed index that answers "what's near here?" and "what's inside this area?" over nodes that carry a geometry. It is domain-agnostic — it stores only ids and geometry — and it is maintained automatically as part of normal transactions. This chapter shows how to make a node type spatial and how to query it.

*** Geometry values

Locations are represented by the ~geometry~ value type. Coordinates are WGS84 and, following the GIS / GeoJSON convention, are written *(lon lat)* order, stored internally as packed ~(simple-array double-float (*))~ vectors (reducing memory overhead by 3–4x and avoiding consing/unboxing during spatial predicates). Four kinds are supported, built with these constructors:


#+BEGIN_SRC lisp
  (make-point lon lat)                 ; a single position
  (make-linestring '((lon lat) ...))   ; a path
  (make-polygon '(exterior-ring hole-ring ...))   ; ring = ((lon lat) ...), or packed double-float vectors
  (make-multipolygon '(polygon ...))   ; polygon = (ring ...)
#+END_SRC

A ~geometry~ is a normal serializable value, so you store one in a node slot just like a string or number. Legacy nested list serializations are transparently upgraded to packed arrays upon deserialization. When optional GEOS integration is loaded, foreign geometries are built directly via GEOS C API FFI calls without WKT text round-trips (~27x faster predicate execution). Useful accessors include ~geometry-kind~, ~geometry-coordinates~ (packed array representation), ~geometry-coordinate-pairs~ (classic nested list of ~(lon lat)~ pairs for exporters and GeoJSON), ~map-geometry-coordinates~ (zero-allocation vertex iterator), ~geometry-lon~ / ~geometry-lat~ (for points), and ~geometry-bbox~ (axis-aligned bounding box as ~(values min-lon min-lat max-lon max-lat)~).



*** Making a node type spatial

To put a node type on the map, give it a geometry slot and mark that slot ~:index t~. That is all it takes: every create/update/delete of such a node then automatically maintains that class's spatial index — there is no separate "add to index" call.

#+BEGIN_SRC lisp
  (def-vertex observation ()
    ((location :type geometry :index t)   ; <- :index t makes it spatial
     (note     :type string))
    :survey-app)

  (with-transaction ()
    (make-observation :location (make-point 37.17d0 49.20d0)
                      :note "sighting near the river"))
#+END_SRC

Under the hood, indexing goes through the ~node-geometry~ generic function, which returns the geometry a node occupies (or ~nil~ — the default — for a node with no location). The ~:index t~ flag wires this up for you: ~node-geometry~'s default method returns the value of the node's indexed geometry slot. You only need to write a ~node-geometry~ method yourself for a *computed* geometry (e.g. derived from several slots, or fetched from a related node); an explicit method takes precedence over the default.

#+BEGIN_SRC lisp
  ;; Equivalent to the :index t form above, and the escape hatch for a
  ;; geometry that isn't simply stored in one slot:
  (defmethod node-geometry ((o observation))
    (slot-value o 'location))
#+END_SRC

*One index per declaring class per geometry slot.* Spatial indexes form a registry keyed ~(owner-class . slot)~, exactly like ~:unique~, ~:vector-index~ and ~:index~. Each spatially indexed class+slot gets its /own/ index, which is what lets a query be scoped to just one class (see /Querying/ below). Two consequences are worth stating:

- A geometry slot declared on a *mixin* gives all of that mixin's subclasses /one shared/ index — the index is owned by the class that /declares/ the slot, not by each subclass. Sibling subclasses are then kept apart at query time by the scope's type filter, not by storage — and that filter runs /inside/ the index scan, so sharing an index costs a scoped query nothing. A class that declares its own geometry slot (no mixin) gets an index to itself.
- Indexes are created *lazily*, on the first geometry-valued write for that class+slot — not by ~make-graph~. A slot marked ~:index t~ that never actually holds a geometry creates no index at all, and a query scoped to it simply returns ~nil~. Each index lives in the graph's index region (~indexes.dat~) and is reopened automatically by ~open-graph~; you never manage it directly.
- *Known limitation — scoping to a parent does not reach a subclass's /own/ extra index.* A scope resolves the /named/ class's geometry slots, but the result type-filter admits subclasses. So if a subclass declares an /additional/ geometry slot of its own, ~(find-nodes-within 'parent …)~ will not scan that subclass-declared index, even though a node stored in it is a ~parent~ by ~typep~. Scope to the exact subclass (or use ~:all~) to reach it. This is not data loss — the node is indexed and findable — only the parent scope misses it; it is folded into the "index a node under every geometry slot" work (GitHub #60), where the multi-index semantics are solved once.

Here is a second spatial type, so the query examples below have two classes to scope across. Because ~sensor~ declares its own geometry slot, it gets its own index, independent of ~observation~'s:

#+BEGIN_SRC lisp
  (def-vertex sensor ()
    ((location :type geometry :index t)
     (kind     :type string))
    :survey-app)
#+END_SRC

*Per-index grid precision and max-cells cap.* A geometry slot may set its index's geohash precision with the ~:spatial-precision~ slot option (default 7, ≈150 m cells — set graph default via ~make-graph~'s ~:spatial-precision~) and its max-cells cap with the ~:spatial-max-cells~ slot option (default 16384 — set graph default via ~make-graph~'s ~:spatial-max-cells~). Coarser grids and lower cell caps suit large area geometries, while finer grids suit dense point data. Changing a declared precision re-grids that one index automatically the next time the graph is opened — on the *on-disk* backend. A ~memory-graph~ reopens its index at the *persisted* precision and does not adopt a changed declaration until you rebuild explicitly; it over-covers at the old grid, so results stay correct but a stale precision costs selectivity rather than accuracy (see #66).


#+BEGIN_SRC lisp
  (def-vertex zone ()
    ((extent :type geometry :index t :spatial-precision 3 :spatial-max-cells 64))  ; coarse grid for big polygons
    :survey-app)
#+END_SRC


*One geometry slot per node is indexed.* A node is indexed by the /first/ geometry-valued indexed slot ~node-geometry~ finds; a second geometry-valued indexed slot on the same class is silently /inert/. Because the effective geometry is decided by value at write time (the ~:type geometry~ declaration cannot be compared reliably across application packages), VivaceGraph reports this by value rather than by declaration: a class whose nodes bind two geometry slots triggers a ~warn~ on the write path — naming the class, the geometry slots found, and which one wins — sampled over the class's first 64 nodes, so it costs nothing steady-state. ~audit-spatial-slots~ (graph) is the exhaustive, read-only counterpart: it sweeps every live node and reports every such class with its winning and inert slots — the thing to run after a migration or wire into a schema test suite.

*** Querying

Two read styles are provided, both refining the index's candidates with exact geometry math.

Every query takes a *scope* as its first argument: a node-class name, a list of names, or ~:all~. The scope both /selects/ which per-class indexes are scanned and /filters/ the results by type. Both halves matter — a geometry slot declared on a mixin gives its subclasses one *shared* index, so storage separation alone would not keep a sibling subclass's nodes out of the answer. Naming a class that is not spatially indexed signals an error; a class whose index simply holds nothing yet returns ~nil~, which is a legitimate empty result.

*Lisp API:*

#+BEGIN_SRC lisp
  ;; Observations within RADIUS metres of a point, nearest first, as (node . distance):
  (find-nodes-near 'observation 49.20 37.17 500.0)

  ;; The K observations nearest a point, nearest first (also (node . distance) pairs):
  (find-nearest-k 'observation 49.20 37.17 5)

  ;; Observations whose location falls inside a :POLYGON / :MULTIPOLYGON area:
  (find-nodes-within 'observation my-task-area)

  ;; A list scope unions the named classes (here OBSERVATION and SENSOR);
  ;; :all scans every index in the graph.
  (find-nodes-within '(observation sensor) my-task-area)
  (find-nodes-within :all my-task-area)
#+END_SRC

~find-nearest-k~ is bounded by ~:max-radius~ (default 25 km): the geohash index answers a window by enumerating its grid cells, so an unbounded nearest-neighbour search is not supported — it returns the K nearest /within max-radius/ (widen it only if you accept the per-query cost, which grows with the square of the radius).

*Prolog functors* (these /yield/ matching nodes, so they compose with the rest of a query):

#+BEGIN_SRC lisp
  ;; All observations within 500 m of (49.20, 37.17):
  (select-flat (?o)
    (find-near ?o observation 49.20 37.17 500.0))

  ;; The 5 observations nearest (49.20, 37.17):
  (select-flat (?o)
    (find-nearest ?o observation 49.20 37.17 5))

  ;; All observations inside a task-area geometry bound to ?area:
  (select-flat (?o)
    (find-within ?o observation ?area))
#+END_SRC

~find-near/5~ takes ~?node scope lat lon radius-metres~; ~find-nearest/5~ takes ~?node scope lat lon k~; ~find-within/3~ and ~find-intersects/3~ take ~?node scope area~. The scope is written as a bare class-name atom (or ~:all~); it already restricts the answer by type, so the ~is-a~ goal these examples once needed is no longer required.

*** Under the hood, and a few caveats

- *The indexes* are ordered indexes (in the graph's index region, ~indexes.dat~) — a skip list by default, or a B+ tree if the graph's ~:index-backend~ selects one (see Chapter 3) — one per spatially indexed ~(class . slot)~, each keyed by the composite ~(geohash-cell . node-id)~: a node's id is entered under every grid cell its geometry occupies, at that index's precision. Folding the id into the key keeps the index *duplicate-free*, so insert and — especially — *remove* are O(log n) (an older duplicate-cell layout made removal O(n)). Each entry also stores the *type tag* of the node it points at, which is what lets a scoped query reject an out-of-scope candidate from the index entry alone, without materialising the node — so a query on an index /shared/ by several classes costs its own results, not the whole index's population. A query covers its window with as few, possibly coarser, cells as it can and does one *prefix range scan* per covering cell — geohash keys are prefix-nested, so every finer cell within a coarse one sorts inside its range — touching only the cells in view. Each index carries its own precision: the ~:spatial-precision~ slot option if the geometry slot declares one, else the graph default (~make-graph~'s ~:spatial-precision~ keyword, default 7 ≈150 m cells; 9 ≈ 5 m). A precision is persisted with its index and read back by ~open-graph~. A graph written before the current scheme (the spatial sidecar is now ~spatial-indexes.dat~, format v5) re-derives /all/ its spatial indexes from the live node geometries on first open — index only, node data untouched, nothing re-fetched.
- *A bounded insert, self-healed at query time.* To stop a huge polygon from covering an astronomical number of fine cells, an insert caps its cover (16384 cells per index) and, when it must, stores that geometry more coarsely. The coarsening is made safe by the same /filter then refine/ contract: each index remembers the coarsest precision it actually holds and a query never covers finer than that, so a coarsely-stored country-scale polygon is still found (then refined exactly). Deleting the oversized geometry lets the finer selectivity return on its own, with no rebuild. Per-index precision (above) is the real control; the cap and clamp are a safety net for data that does not match the grid. The cap bounds a /whole geometry's/ cover: a multipolygon is covered part by part (so the gaps between separated parts are not indexed) but at one precision — the finest whose total fits — so a small island in a large boundary keeps full precision rather than dragging the index's clamp down with it (GH #103).
- *Matching uses a representative point*: a ~:point~ matches exactly; an extended geometry (line, polygon) is matched by the centre of its bounding box, so radius/containment results for extended geometries are approximate. Point-in-polygon refinement honours holes.
- *Distance* is the haversine great-circle distance — accurate to roughly half a percent, ample for most uses; a more precise geodesic can replace it later without changing the API.
- *Heavier topology* (intersection, union, validity repair) is intentionally out of this dependency-free core and is left to an optional GEOS-backed module.

*** Subset replication (field devices)

A replication *slave* can hold only a subset of the master's data — useful for a field device that needs just its area of operations, not the whole dataset. Give the slave a ~:replication-filter~: a predicate ~(node) -> boolean~ that decides, per replicated write, whether the slave applies it. Each transaction still advances the slave's high-water mark, so filtered transactions are not re-requested.

~make-spatial-replication-filter~ builds a filter from an area geometry. It accepts a node when it has /no/ geometry (so schema and reference data replicate in full) or when its geometry lies in the area:

#+BEGIN_SRC lisp
  (make-graph :ops-app "/data/field-laptop/"
              :slave-p t :master-host "hq.example.org" :replication-port 5432
              :replication-filter
              (make-spatial-replication-filter my-area-of-operations))
#+END_SRC

This is a prototype: end-to-end master/slave streaming is exercised by the harness in =tests/replication/=, and a node that /moves/ across the area boundary on an update is not yet reconciled.

*** Exact topology with GEOS (optional)

The dependency-free refine layer answers "is this point in this area" exactly, but it judges an /extended/ geometry (a polygon or line node) only by a representative point, and it has no polygon↔polygon intersection or validity repair. For exact topology, load the optional ~graph-db/geos~ system, a thin in-house CFFI binding to the GEOS C library (~libgeos_c~):

#+BEGIN_SRC lisp
  (ql:quickload :graph-db/geos)   ; needs libgeos_c (e.g. brew install geos)
#+END_SRC

Core ~graph-db~ never depends on libgeos. Loading the add-on binds the library if present and flips ~*geos-available-p*~; if the library is missing it logs a warning and leaves the flag NIL — the seam below simply keeps using the fallbacks. So the add-on is safe to load unconditionally.

The add-on /upgrades/ a set of generic functions in place (no API change). When it is loaded:

- ~find-nodes-within~ judges extended-geometry nodes by **exact containment**, not their bbox centre.
- ~find-nodes-intersecting~ / ~find-intersects/3~ become **exact** (without GEOS they fall back to a coarse bounding-box overlap).
- ~geometry-intersects-p~, ~geometry-contains-geometry-p~ answer exactly for all geometry kinds.
- ~geometry-make-valid~ repairs an invalid geometry (e.g. a self-intersecting polygon from a messy KML); ~geometry-valid-p~ tests validity. (~make-valid~ needs GEOS >= 3.8.)
- ~geometry-distance-exact~ gives planar distance — note this is in *coordinate units* (degrees for lon/lat), not metres; use ~geodesic-distance~ / ~geometry-distance~ for metric distance between points.

#+BEGIN_SRC lisp
  ;; nodes whose footprint actually overlaps the area (exact with GEOS):
  (find-nodes-intersecting 'observation my-task-area)

  ;; repair a self-intersecting polygon before indexing it:
  (let ((clean (geometry-make-valid messy-polygon)))
    (with-transaction () (make-observation :location clean)))
#+END_SRC

Threading: GEOS's reentrant API forbids sharing a context between concurrent threads, and VivaceGraph runs transactions in the caller's thread. The add-on keeps a process-global **borrow/return context pool** (~with-geos-context~): each operation checks out a context for its duration, so a context is only ever used by one thread at a time, and contexts are reused across threads (bounded by peak concurrency). ~geos-shutdown~ releases the pool. This is validated under a concurrency storm and cross-checked against Python ~shapely~ in =tests/geos/=.

** Chapter 14: Graph Algorithms

VivaceGraph ships an optional *graph-algorithms* add-on — classic analysis algorithms (shortest paths, ranking, components, flow, random-graph generation) that run over a real, persistent graph. It is the ~graph-db/algorithms~ system, and it depends only on the embeddable core (~graph-db/core~), so it is usable from a headless deployment with no HTTP layer:

#+BEGIN_SRC lisp
  (ql:quickload :graph-db/algorithms)
#+END_SRC

*** Two execution modes

The algorithms come in two families, chosen by how they relate to scale:

- *Native (streaming).* Algorithms that walk the live adjacency indexes directly, keyed by node id (UUID), under a single consistent read snapshot. They never materialize the whole graph, so they suit large, persistent data. This family covers shortest paths, BFS structure, degree, and the ranking algorithms.
- *Projection (in-memory).* Algorithms that are inherently global — all-pairs shortest paths, clustering, max-flow — need a compact, freely-mutable working copy. ~with-graph-projection~ materializes (a slice of) the graph into an in-memory copy under a snapshot, runs the algorithm there, and maps results back to vertices. The persistent graph is *never mutated*; clustering and flow disturb only the throwaway projection.

Every algorithm is *read-only* with respect to the stored graph and runs under the MVCC read-snapshot machinery (Chapter 12), so a long analysis sees a stable view even under concurrent writers. Nodes are ordinary vertex objects, exactly as the rest of the API produces and consumes them; a "node designator" argument also accepts a vertex's id (a key vector or its string form).

*** Shortest paths

~shortest-path~ is weighted Dijkstra by default (edge ~weight~ is the cost); pass ~:unweighted t~ for hop counts, or a ~:heuristic~ to turn it into A*. It returns ~(values path cost)~ — the ordered vertex list and its total weight — or ~(values nil nil)~ when the target is unreachable.

#+BEGIN_SRC lisp
  ;; weighted shortest path between two vertices:
  (shortest-path origin destination)                 ; => (values (v0 v1 .. vn) cost)

  ;; treat edges as undirected, count hops not weights:
  (shortest-path a b :direction :both :unweighted t)

  ;; A* with an admissible heuristic h(vertex, target) -> estimated remaining cost:
  (a-star a b (lambda (v target) (straight-line-km v target)))

  ;; distances from one source to every reachable node, ascending:
  (single-source-shortest-paths origin)              ; => ((vertex . distance) ...)
#+END_SRC

~:direction~ is ~:out~ (default), ~:in~, or ~:both~; ~:edge-type~ restricts the walk to a single edge type /or a list of edge types/ (their union); ~:weight-fn~ overrides how an edge's cost is read. Dijkstra/A* require non-negative weights. Throughout the algorithm layer, every ~:edge-type~ argument accepts either a single type or a list of types.

*** Structure

Matrix-free structural queries, all native:

#+BEGIN_SRC lisp
  (degree v)                 ; total incident edges (in + out); also out-degree / in-degree
  (degree-distribution)      ; sorted ((degree . count) ...), :which :total|:out|:in
  (distance-map source)      ; BFS hop distances: ((vertex . hops) ...), ascending
  (connected-components)     ; list of vertex lists, largest first (weakly connected)
  (spanning-tree :root v)    ; (values tree-edges root); edges are (parent . child) conses
  (graph-center)             ; (values center-vertices min-eccentricity)
#+END_SRC

~connected-components~ and ~graph-center~ default to ~:direction :both~ (undirected semantics). ~graph-center~ is the BFS-eccentricity form — a breadth-first search per vertex, O(V·(V+E)); scope it with ~:vertex-type~ on a large graph, or use the projection all-pairs (below) for the matrix form.

*** Ranking

#+BEGIN_SRC lisp
  ;; PageRank: (values ranked-list iterations), ranked descending as (vertex . rank).
  ;; Iterates to an L1 convergence tolerance (not a fixed step count), redistributes
  ;; dangling-node mass so ranks sum to 1, and caps iterations.
  (page-rank :damping 0.85d0 :tolerance 1d-6)

  ;; HITS hubs & authorities: (values authorities hubs iterations).
  ;; Both vectors are L2-normalized every iteration.
  (hub-authority-values)

  ;; SimRank similarity of two nodes (recursive, depth-bounded, memoized):
  (sim-rank a b :max-depth 5 :decay 0.8d0)
#+END_SRC

*** All-pairs, clustering, and cut (projection)

These build an in-memory projection. ~all-pairs-shortest-paths~ (Floyd–Warshall) returns a result object you query, rather than an O(V²) table of vertex pairs:

#+BEGIN_SRC lisp
  (let ((apsp (all-pairs-shortest-paths :directed t)))
    (apsp-distance apsp a b)    ; shortest distance, or NIL if unreachable
    (apsp-path apsp a b))       ; ordered vertex list, or NIL

  ;; edge-betweenness (default) or edge-span clustering; removes the top edges and
  ;; returns them as (from-vertex to-vertex score):
  (graph-clustering :method :edge-betweenness :edge-removal-count 1)

  ;; a minimal edge cut, as (from-vertex to-vertex) pairs:
  (minimum-cut)
#+END_SRC

All-pairs is O(V²) memory / O(V³) time — it warns you to scope large graphs with ~:vertex-type~. For direct control of the working copy, ~with-graph-projection~ binds a projection you can query with ~projection-index~ / ~projection-vertex~.

*** Maximum flow and matching (projection)

Edge ~weight~ is treated as capacity. Flow runs on a residual copy, so the stored graph is untouched.

#+BEGIN_SRC lisp
  ;; (values flow-value flow-edges); flow-edges are (from to flow).
  (maximum-flow source sink :algorithm :dinic)

  ;; is the graph bipartite? -> (values t partition-a partition-b) or (values nil ..):
  (bipartite-p)

  ;; maximum bipartite matching as (vertex1 vertex2) pairs:
  (maximum-matching :algorithm :dinic)
#+END_SRC

Three max-flow algorithms are available — ~:edmonds-karp~ (default), ~:dinic~, and ~:goldberg-tarjan~ (push-relabel) — and all agree on the (unique) maximum-flow value.

*** Generating random graphs

The generators persist a random topology into a real graph in one transaction. They are schema-agnostic: you supply the constructors, the model decides the wiring.

#+BEGIN_SRC lisp
  ;; an Erdős–Rényi G(n, p) of 100 'city' vertices joined by 'road' edges:
  (generate-graph :erdos-renyi 100 :p 0.05
                  :vertex-constructor (lambda (i) (make-city :name (format nil "c~D" i)))
                  :edge-constructor   (lambda (from to) (make-road :from from :to to)))

  ;; Barabási–Albert preferential attachment:
  (generate-graph :barabasi-albert 100 :vertex-constructor #'... :edge-constructor #'...)
#+END_SRC

~:vertex-constructor~ is called with each node index ~(0 … size-1)~ and returns a vertex; ~:edge-constructor~ is called with ~(from-vertex to-vertex)~. Both run inside the builder's transaction.

*** Importing and visualizing (~graph-db/algorithms-io~)

Import from standard graph file formats and export to Graphviz live in a *separate* optional system, ~graph-db/algorithms-io~, so its parsing dependencies (~yacc~, ~dso-lex~, ~parse-number~) stay out of the core add-on:

#+BEGIN_SRC lisp
  (ql:quickload :graph-db/algorithms-io)

  ;; import a GML or Pajek (.net) file; same schema-agnostic constructor contract
  ;; as generate-graph, plus a label / weight from the file:
  (import-gml   "graph.gml"
                :vertex-constructor (lambda (i label) (make-city :name label))
                :edge-constructor   (lambda (from to weight)
                                      (make-road :from from :to to :weight weight)))
  (import-pajek "graph.net" :vertex-constructor #'... :edge-constructor #'...)

  ;; write a DOT file and render it (needs Graphviz's `dot` on PATH):
  (visualize :file "/tmp/g.dot" :render :hierarchical :format "svg"
             :label-fn (lambda (v) (slot-value v 'name)))
  ;; or just emit DOT to a stream:
  (graph->dot :stream *standard-output* :label-fn #'...)
#+END_SRC

*** Prolog predicates

The native algorithms are also exposed as Prolog functors, so analysis composes with the query language (Chapter 6). Like the spatial functors, they /yield/ solutions:

#+BEGIN_SRC lisp
  ;; the weighted shortest path (and its cost) between two pinned vertices:
  (select (:flat nil) (?path ?cost)
    (is-a ?from city) (node-slot-value ?from name "A")
    (is-a ?to   city) (node-slot-value ?to   name "Z")
    (shortest-path ?from ?to ?path ?cost))

  ;; every node's PageRank (the node arg may be bound to filter, or unbound to enumerate):
  (select (:flat nil) (?node ?rank) (page-rank ?node ?rank))
#+END_SRC

The predicates are ~shortest-path/4~ (From To Path Cost), ~distance/3~, ~reachable/2~, ~connected-component/2~, ~degree/2~, ~page-rank/2~, ~authority-value/2~, and ~hub-value/2~. They are pure reads, so they run even under a read-only ~:effects nil~ query. (As with any functor, a query written in a package other than ~graph-db~ must import the predicate's ~name/arity~ symbol — see Chapter 7.)

*** Caveats

- *Recompute cost.* ~page-rank/2~, ~authority-value/2~, and ~hub-value/2~ recompute the whole ranking on each call; for repeated use, call the Lisp ~page-rank~ / ~hub-authority-values~ once and keep the result.
- *Not ported (broken upstream).* The Karzanov max-flow algorithm, the Viger–Latapy generator, and node-capacity max-flow were intentionally left out of the port — the source implementations did not satisfy the max-flow invariant, hung, or were otherwise unreliable. Only edge capacities are supported for flow.


** Chapter 15: The In-Memory Backend (~memory-graph~)

Everything in Chapters 3–14 assumed VivaceGraph's on-disk storage engine — the memory-mapped heap, the linear-hash tables, deserialize-on-read. VivaceGraph also ships a second, explicitly-constructed storage backend that keeps the entire graph as *live Lisp objects in RAM*. It is a drop-in alternative: the same schema, transactions, Prolog queries, views, spatial index, and even (peer) replication all work unchanged. Only the construction call differs.

Why a second backend? The on-disk engine's great strength — working with a graph far larger than RAM, paged in and out by the operating system (Chapter 3) — becomes a cost on a small graph that fits in memory. There, every read pays *deserialization* (rebuilding a Lisp object from the heap's bytes) and every adjacency walk chases persistent cons cells. The in-memory backend removes both: a read returns the live object itself, and adjacency is an in-RAM hash set. On a small, hot working set — a mobile field application, an ECL image running on a phone — this is dramatically faster; on real on-device query/render workloads it is 8–80× quicker once loaded, at the cost of holding the whole graph resident.

*** Constructing an in-memory graph

Swap ~make-graph~ / ~open-graph~ for ~make-memory-graph~ / ~open-memory-graph~. Everything else is identical:

#+BEGIN_SRC lisp
  (defvar *g* (make-memory-graph :my-app "/var/tmp/mem-app/"))
  (let ((*graph* *g*))
    (with-transaction ()
      (make-person :name "Alice" :age 30))
    (select-flat (?p) (is-a ?p person)))     ; queries work exactly as before
#+END_SRC

The ~location~ directory is still required, but it now holds only the *durable* artifacts — the transaction journal, the schema, a checkpoint image, and (for a peer) the peer state. The RAM structures are rebuilt from them on ~open-memory-graph~.

An in-memory graph is a distinct graph *class*, chosen at construction; the on-disk engine is left entirely untouched. It has no memory-mapped heap (~(heap g)~ is ~nil~), no buffer pool, and no persistent free list, so you pass neither ~:buffer-pool-size~ nor any heap-tuning option.

*** What changes under the hood

The graph model, transaction machinery, and query surface are all shared; the in-memory backend simply overrides the small set of storage primitives they call:

| On disk | In memory |
|---|---|
| Linear-hash vertex/edge tables (~linear-hash.lisp~) | A hash table of UUID → live node object |
| Heap-stored, serialized slot data; deserialize on read | Slot data lives on the live object; no per-read work |
| Persistent ~index-list~ adjacency (ve/vev/type indexes) | In-RAM hash sets mirroring the same index shapes |
| On-disk ordered indexes (skip list or B+ tree) for views and the spatial grid | In-RAM skip-lists (~mem-skip-list~) with the same cursor API |
| Heap allocate/free + MVCC version chains | Atomic hash-table swap of an immutable node; no heap |

Because the graph model, `with-transaction`, OCC validation, and the Prolog engine are unchanged, code written against an on-disk graph runs against an in-memory graph verbatim.

*** Durability: journal + checkpoint image

Having no heap, an in-memory graph's durable record is the same write-ahead transaction journal (the ~.txn~ files) the on-disk engine produces — here *retained* rather than folded into a heap. On top of the journal it keeps a *checkpoint image*: a single file (~graph.img~) written at each clean ~close-graph~ that captures the whole graph — the node tables *and* the derived structures (indexes, spatial grid, views). Opening restores that image in one read, then replays any journal entries committed after it.

- *Clean close* → the image is written and the journal cleared; the next open restores the image quickly.
- *Crash* (no clean close) → the retained journal replays on the next open. An in-memory graph tolerates a ~.dirty~ marker: it always rebuilds from its durable journal + image, so an unclean shutdown is *recovered*, not an error (contrast Chapter 3).

Persisting the derived structures in the image — rather than rebuilding them on open — is what keeps open fast; rebuilding aggregate (reduce) views in particular is expensive.

You may force a checkpoint at any time with ~checkpoint-memory-graph~, which writes the image and clears the journal *now*, without closing. This matters for a *peer device* (Chapter 16): pulled state is applied directly and is not journaled, so it is durable only through the image. Call ~checkpoint-memory-graph~ after a ~peer-sync~ so a restart need not re-sync the pulled subgraph.

*** Eager vs. lazy: the open-latency trade-off

The one tuning decision an in-memory graph exposes is *when* it builds the live node objects. Constructing a node — a CLOS instance carrying its slot data — is the dominant cost of opening a large in-memory graph (on ECL, roughly 85% of restore time; the wire format and byte-parsing are almost free by comparison). The ~:lazy~ option chooses whether you pay that cost up front or on demand.

**** Eager (the default)

With no ~:lazy~ argument, ~make-memory-graph~ / ~open-memory-graph~ build *every* node at open. Steady-state reads are then a bare hash-table lookup — the fastest possible — but open pays to construct every node whether or not you go on to touch it. Prefer eager when the whole graph *is* the working set, or when open latency simply does not matter.

**** Lazy — fault-on-access (~:lazy t~)

#+BEGIN_SRC lisp
  (make-memory-graph :my-app dir :lazy t)
  (open-memory-graph  :my-app dir :lazy t)
#+END_SRC

A lazy graph loads each node as a compact *blob* (its parsed head plus its still-serialized slot data) and builds the live object only on first touch, caching it thereafter. Open therefore does *no* object construction — it is near-instant regardless of graph size. The consequences:

- *Open is ~O(1)~* in the number of nodes, dominated only by reading the image bytes. Measured on ECL: ≈502 ms → 7 ms (800 nodes) and ≈1269 ms → 18 ms (2000 nodes) — about 71× faster.
- *Aggregate (reduce) views touch zero nodes* — they read the persisted aggregates, so a ~summary~-style query is instant with no materialization at all.
- *Rendering N objects* builds exactly those N (deferred off the open path). Total build cost is conserved, but it is paid only for what you use, never for untouched nodes.
- *Lower RAM* — untouched nodes stay compact blobs rather than full CLOS instances.

Caveats: a *full* scan (e.g. ~map-vertices~ over everything) still materializes everything — lazy wins for *partial* working sets, which is the field case. A lazy graph uses the VG-native image format (written automatically on checkpoint/close), so run one checkpoint on it before relying on the fast open. ~:lazy~ composes with the peer device — it is purely a storage-mode flag.

| | Eager (default) | Lazy (~:lazy t~) |
|---|---|---|
| Open latency | Builds every node (~O(nodes)~) | Near-instant (~O(1)~) |
| First touch of a node | Free (already built) | Builds + caches it |
| Aggregate views | Instant | Instant (touch no node) |
| Full scan | Same as eager | Materializes everything |
| Resident RAM | All nodes as objects | Untouched nodes stay blobs |
| Best for | Whole graph is the working set | Large scope, partial reads, fast boot |

*** What the in-memory backend omits

Two on-disk features are deliberately dropped:

- *MVCC version chains.* On disk, an update archives the prior version's head into the heap and chains to it (Chapter 12). An in-memory graph is single-writer and publishes a new immutable node by an atomic hash-table swap, so a lock-free reader always observes a whole node, never a torn one. The ~with-read-snapshot~ / ~:snapshot~ API is kept (as a writer-excluding read lock), but there is no version *history* to reconstruct.
- *Heap garbage collection.* There is no heap to compact; ~gc-heap~ is a safe no-op on an in-memory graph.

*** When to use it

- The graph (or the working set you keep open) fits comfortably in RAM.
- Read/traversal latency matters more than resident memory — interactive or mobile use.
- You are targeting ECL on a device, where per-read deserialization is especially costly.
- You want a general-purpose in-memory graph for a non-replicated, ephemeral, or test workload.

Reach for the on-disk engine instead when the graph is larger than RAM, when you need the MVCC version history, or when a modest resident-memory footprint is more important than read latency.

** Chapter 16: Peer Replication — Offline-First Hub-and-Spoke

The master-slave replication of Chapter 10 assumes always-connected, read-only replicas that mirror the *entire* master. That model does not fit an offline-first mobile fleet, where each device is only intermittently connected, holds just the *subset* of data it is authorized to see, and must *author* changes locally while disconnected. VivaceGraph's *peer replication* (in the ~graph-db/replication~ system) addresses exactly this, through a separate ~peer-graph~ abstraction. The master/slave classes and protocol of Chapter 10 are left byte-for-byte as they are; peer replication is an additional mode, not a change to the old one.

*** The model

- *Star topology.* One *hub* and many *devices*. Devices sync only with the hub, never peer-to-peer. Every sync cursor is a single scalar per directed feed — there are no vector clocks anywhere.
- *Bidirectional.* A device *pulls* the authority-scoped subset it is allowed to see, and *pushes* the changes it authored while offline. The hub is the single linearization point.
- *Authority-scoped, fail-closed.* Each device receives only the *closed subgraph* it is cleared for. A vertex ships only if it is disclosable to that device; an edge ships only if *both* of its endpoints are — otherwise it is omitted entirely. VivaceGraph never ships a read-only stub, because a stub would leak the very existence and id of undisclosed work. When a node enters a device's scope it ships as a create; when it leaves, the hub sends a *purge*.

*** Four identities

Peer replication is careful to keep four distinct identities apart — conflating any two of them is a whole class of bug:

1. *Node UUID* — the identity of the thing (vertex or edge). The idempotency key for state-sync.
2. *Original-op id* — the identity of an authored change *event*; minted by the authoring replica and stable across re-homing. It is the dedup key, so an op a device authored, which later bounces back to it through the hub feed, is recognized and not re-applied.
3. *Per-origin feed sequence* — a position in a directed feed (the existing per-graph ~tx-id~). It drives the resumable pull cursor. Re-homing re-assigns it.
4. *Lamport stamp* — the conflict order for per-field last-writer-wins. It travels with the field value and *survives* re-homing.

Identity 2 answers "have I already applied this event?"; identity 4 answers "which of two conflicting values wins?" — different jobs, never the same field.

*** Two op classes

The feed carries two kinds of traffic, with different rules:

- *Authored ops* — a user or automation change (a create, a field edit, an authored delete). They carry origin-id + original-op-id + Lamport stamp, are deduped by op-id, and are *bidirectional* (devices author them; the hub re-homes them onto its own feed).
- *State-sync ops* — the hub asserting the *current membership* of a device's authority scope. They are keyed by node UUID (idempotent by identity), flow hub→device only, and are never deduped by op-id, propagated back, or merged. A node entering scope ships as a full create; a node leaving scope ships as a *purge* — "remove this from *your* replica," distinct from a delete (the node still exists on the hub).

*** Conflict resolution

When two replicas edit the same node, the hub re-homes the device's authored op and resolves it per field by Lamport-ordered last-writer-wins, with an app-supplied *merge policy* for safety-bearing fields. A rejected change is not silently dropped — it surfaces as a *conflict record* the application can inspect. Safety-critical fields resolve by *semantics, not clock*: for example, a hazard *release* loses to a hazard *assertion* regardless of which carries the later timestamp.

The merge above is *per field of the same node* (keyed by UUID). Unique-slot constraints (Chapter 8) are a different axis — two *different* nodes claiming one value — and are handled by *scope*. A ~:scope :origin~ constraint partitions by authoring device, so it never collides across devices and each device enforces it locally against everything it holds; this is the recommended choice under peer replication. A value that must be unique across the *whole* fleet (~:scope :local~/~:hub~) needs the hub to arbitrate colliding claims — that arbiter is not yet built (issue #51).

*** Setting up a hub and a device

The hub authors data normally (Chapters 4–5) and additionally exposes an *export predicate* — the app-owned ~disclosable-p~ function that decides, per vertex and per requesting device, what may be shared. (The device registry mapping a device to a person/team and a clearance scope is likewise app-owned; the engine consumes only the resulting origin-id + predicate + cursors.)

#+BEGIN_SRC lisp
  ;; Hub process:
  (defvar *hub*
    (make-graph :field-app "/var/tmp/hub/"
                :peer-role :hub
                :replication-port 7979
                :replication-key "shared-secret"
                :export-predicate #'my-disclosable-p))
#+END_SRC

A device is constructed with a hub-minted ~:origin-id~ (an opaque 16-byte id) and the hub's address, then calls ~peer-sync~ to both pull its scope and push what it authored:

#+BEGIN_SRC lisp
  ;; Device process:
  (defvar *dev*
    (make-graph :field-app "/var/tmp/device/"
                :peer-role :device
                :origin-id *my-hub-minted-origin*
                :peer-host "hub.example.org"
                :replication-port 7979
                :replication-key "shared-secret"))

  ;; author locally, even while offline...
  (let ((*graph* *dev*))
    (with-transaction () (make-observation :note "found something")))

  ;; ...then reconcile when connectivity returns: pull scope + push authored ops
  (peer-sync *dev*)
#+END_SRC

As with master/slave, a *minor* schema drift (same major version) still syncs, degraded-safe; a *major* mismatch is rejected before any data moves.

*** Peer replication over the in-memory backend

The storage backend is orthogonal to the replication role: ~make-memory-graph~ accepts the very same peer arguments, yielding an *in-memory peer device* — the intended mobile/ECL configuration. Combined with ~:lazy t~ and a post-sync ~checkpoint-memory-graph~, such a device gets a near-instant open plus fault-on-access reads of its synced subgraph (Chapter 15).

** Chapter 17: Multiple Graphs in One Image

VivaceGraph supports opening several graphs in one Lisp image. This chapter states
the contract; it is enforced, not advisory.

*** A read-write transaction belongs to exactly one graph

The transaction manager is per graph. ~with-transaction~ defaults to
~(transaction-manager *graph*)~, each graph has its own transaction-id counter, its own
committed-transaction set for validation, and its own write-ahead log. Touching a node
whose home graph differs from the transaction's — reading it *or* writing it — signals
~cross-graph-transaction-error~.

This is not a restriction added for convenience; it is what atomicity and durability
already mean here. A transaction spanning two graphs would need a global ordering across
independent counters and two-phase commit across two logs. Without 2PC, a crash between
the two commits leaves one graph committed and the other not.

To write to several graphs, use one transaction per graph and sequence them yourself.
*That coordination is not atomic.* If the second transaction fails, the first has already
committed, and nothing rolls it back. Design for that, or keep the invariant inside one
graph.

*** The rule covers the transactional path, not literally every read

"Touching a node ... signals" means every read that resolves through ~lookup-object~
(~lookup-vertex~, ~lookup-edge~, and any typed scan built on them) and every mutation entry
point — ~create-node~, ~save~/~update-node~, ~delete-node~/~mark-deleted~. Two call paths
read a node's storage without going through that check. ~copy~'s ~maybe-init-node-data~ may
fault a node's bytes in from its own home graph's heap while a read-write transaction on a
*different* graph is active; the misuse is still caught one step later, at the following
~save~. And a fully untyped ~map-vertices~/~map-edges~ scan (no ~:vertex-type~) walks the
lhash directly and never reaches ~lookup-object~ — consistent with "A note on scans" in
Chapter 12, which documents that untyped scans bypass MVCC entirely and are meant for
quiescent, read-only passes. Scanning a foreign graph that way from inside a read-write
transaction reads without a pin; the result is correct only if the other graph is quiescent,
and that is the caller's responsibility, not something the engine checks.

*** Read-only snapshots are per graph and compose

~with-read-snapshot~ records its snapshot per graph, so several may be active at once. A
query may hold one snapshot per participating graph, each internally consistent and
repeatable.

There is deliberately *no single instant across graphs*: two graphs may be observed at
different logical moments. A cross-graph instant would need an epoch shared by every
transaction manager, which is not implemented.

A read-write transaction takes precedence and does *not* fall through to a snapshot. If a
read-write transaction on graph A is active, reading graph B signals — even if a snapshot
of B exists. Satisfying that read from a different consistency domain would be worse than
refusing it.

*** Nodes know which graph they came from

Every node carries its home graph. A node's heap, tables and schema resolve through that
rather than through the ambient ~*graph*~, so a node found via an explicit ~:graph~ reads
correctly whatever ~*graph*~ happens to be bound to. The value is never serialized.

One consequence worth knowing: a node retained past its graph's ~close-graph~ now
dereferences an unmapped heap rather than silently decoding whatever lies at that offset
in another graph's file. Do not hold nodes across a close.

*** Class names are global

Common Lisp has one class namespace, so a node class name must be unique across *all*
graph schemas. Defining the same name for a second graph signals
~duplicate-node-class-error~. Redefining a type under the *same* graph name remains
legal — that is ordinary schema evolution and works at runtime.

Previously a second definition silently replaced the first class's slots, leaving the
first graph's stored data unreachable through the API while still on disk.

*** ~*transaction*~ is NIL inside a read-only snapshot

~with-read-snapshot~ (and ~select~/~do-query~ with ~:snapshot t~) records its snapshot per
graph in ~*read-snapshots*~ rather than binding ~*transaction*~, so code that reads
~*transaction*~ to tell whether it is inside a query sees ~NIL~ there. Call
~(read-transaction &optional graph)~ instead: it returns the read-write ~*transaction*~ when
one is active and covers ~graph~, else ~graph~'s read snapshot from ~*read-snapshots*~, else
~NIL~. This has second-order effects inside a snapshot: ~copy~ now signals
~no-transaction-in-progress-warning~, ~commit~/~rollback~ now signal
~no-transaction-in-progress~, and ~make-<type>~/~mark-deleted~ now auto-wrap their own real,
committing transaction instead of silently joining a snapshot that was never going to
commit.

Also note: ~graph~ is now a *reserved* slot name on node classes — it backs the ~:META~
home-graph tracking slot described above. A user-defined slot named ~graph~ shadows it and
silently disables home-graph tracking for that class; do not use it as a slot name.

** API Reference

This chapter provides a categorized reference for the most important exported symbols from the ~graph-db~ package. It is not an exhaustive list of every internal function but focuses on the public API you will use most often when building applications.

*** A categorized list of the most important exported functions and macros

**** Graph Management
- ~make-graph (name location &key index-backend ... )~ ::
  Creates a new, empty graph database at the specified ~location~. The ~name~ must be a keyword and should match the graph name used in your schema definitions. ~:index-backend~ (~:skip-list~, the default, or ~:bplus-tree~) selects the ordered-index engine for this graph's views/unique/spatial indexes; it defaults to the global ~*index-backend*~. Returns a `graph` object. See Chapter 3, "Ordered indexes and pluggable backends."

- ~open-graph (name location &key index-backend ... )~ ::
  Opens an existing graph database from ~location~. Fails if the database was not closed cleanly (i.e., if the ~.dirty~ file exists). ~:index-backend~ governs only *new* indexes created after open; each existing index reopens on the backend it was written with (its persisted tag). Returns a `graph` object.

- ~make-memory-graph (name location &key lazy peer-role origin-id peer-host ... )~ ::
  Like ~make-graph~, but constructs an *in-memory* graph (Chapter 15): the graph lives as live Lisp objects in RAM, with the same schema/transaction/query API. ~location~ still holds the durable journal, checkpoint image, schema and peer state. Pass ~:lazy t~ for fault-on-access materialization (near-instant open); accepts the same peer arguments as ~make-graph~ for an in-memory peer device.

- ~open-memory-graph (name location &key lazy peer-role ... )~ ::
  Reopens an in-memory graph, restoring it from its checkpoint image and replaying the retained journal tail. Tolerates a ~.dirty~ marker (it always rebuilds from the durable journal + image). Pass ~:lazy t~ to restore nodes as deferred blobs.

- ~checkpoint-memory-graph (graph)~ ::
  Forces an in-memory graph to write its checkpoint image and clear the journal *now*, without closing. Call after a ~peer-sync~ on a device so pulled (un-journaled) state survives a restart.

- ~close-graph (graph &key snapshot-p)~ ::
  Safely closes the graph database, ensuring all data is written to disk and all file locks are released. By default, it creates a final snapshot before closing. For an in-memory graph this writes the checkpoint image and clears the journal.

- ~lookup-graph (name)~ ::
  Retrieves a handle to an already opened graph by its keyword ~name~.

- ~*graph*~ ::
  A special dynamic variable that should be bound to the currently active graph instance for most operations to work correctly.

- ~graph-stats (&key graph detail-p)~ ::
  Returns an alist of performance statistics for the graph, including free memory, cache size, read/write rates, and node counts.

**** Schema Definition
- ~def-vertex (name (parent-classes) (slot-definitions) graph-name)~ ::
  A macro to define a new vertex class. It inherits from its ~parent-classes~ (which must include ~vertex~), defines its data ~slots~ using standard CLOS syntax, and associates it with the graph named ~graph-name~. Automatically creates a ~make-<name>~ constructor function.

- ~def-edge (name (parent-classes) (slot-definitions) graph-name)~ ::
  A macro to define a new edge class. Similar to ~def-vertex~, but the class must inherit from ~edge~.

**** Transactions
- ~with-transaction ( &body body)~ ::
  A critical macro that wraps a block of database write operations in an ACID transaction. The transaction is automatically committed on successful completion or rolled back on error. All creates, updates, and deletes must occur within this macro.

- ~commit ( &optional transaction)~ ::
  Manually commits the current ~*transaction*~. Rarely needed, as ~with-transaction~ handles this automatically.

- ~rollback ( &optional transaction)~ ::
  Manually rolls back the current ~*transaction*~.

**** Node Operations (CRUD)
- ~make-<class-name> (&key ... )~ ::
  Constructor functions automatically generated by ~def-vertex~ and ~def-edge~. Use these to create new nodes within a transaction. For example, `(make-user :name "Alice")`.

- ~lookup-vertex (id &key graph)~ ::
  Retrieves a vertex object from the database given its 16-byte UUID or string representation.

- ~lookup-edge (id &key graph)~ ::
  Retrieves an edge object from the database given its ID.

- ~copy (node)~ ::
  Creates a mutable copy of a node. This is the *required* first step for updating a node.

- ~save (node-copy &key graph)~ ::
  Saves a modified node copy back to the database, finalizing an update. Must be called on a node that was created via ~copy~ within the same transaction.

- ~mark-deleted (node)~ ::
  Marks a node as deleted. This is a "soft delete" and must be done within a transaction.

- ~id (node)~ ::
  Returns the 16-byte UUID of a node.

- ~from (edge)~, ~to (edge)~, ~weight (edge)~ ::
  Accessors for the core properties of an edge object.

- ~data (node)~ ::
  Returns the raw data alist associated with a node. It is generally recommended to use the standard slot accessors (e.g., `(name my-user)`) instead of this.

**** Prolog Querying
- ~select (options-plist vars-list &rest goals)~ ::
  The primary macro for querying the graph. Executes a series of Prolog ~goals~ and returns a list of solutions for the specified ~vars-list~.

- ~select-flat (vars-list &rest goals)~ ::
  A convenience macro, equivalent to `(select (:flat t) ...)`, which returns a single flat list of results.

- ~select-one (vars-list &rest goals)~ ::
  A convenience macro that returns only the first value of the first variable from the first solution. Extremely useful for lookups.

- ~def-global-prolog-functor (name/arity (args cont) &body body)~ ::
  A macro to extend the query language with a new, custom predicate written in Lisp.

- `(<- (head) . (body))` ::
  A macro for defining Prolog rules.

**** Views & Indexing
- ~def-view (view-name sort-order (class-name graph-name) &body body)~ ::
  Defines a new view (index). The body must contain a ~:map~ clause and may contain an optional ~:reduce~ clause for aggregation.  *Declarative and idempotent* (like ~def-vertex~/~def-edge~): the graph need not be open when ~def-view~ runs — a view can be co-located with its ~def-vertex~/~def-edge~ and loaded before ~open-graph~, which reconciles it at open time.  Re-evaluating an *unchanged* ~def-view~ (or simply restarting) does **not** rebuild the persisted index — restart is O(1).  Changing the ~:map~/~:reduce~ code or sort order rebuilds the index and emits a ~log:warn~.  Deleting a ~def-view~ form does not drop the persisted index; use ~delete-view~ for that.

- ~invoke-graph-view (class-name view-name &key key start-key end-key ... )~ ::
  The primary function for querying a view. Use the `:key` argument for point lookups or `:start-key` and `:end-key` for range scans. Use `:group-p t` to query the aggregated results of a reduce view.

- ~map-view (function class-name view-name &key ... )~ ::
  A lower-level function to iterate over the results of a map-only view and apply a function to each result.

- ~map-reduced-view (function class-name view-name &key ... )~ ::
  Iterates over the aggregated results of a map-reduce view.

- ~regenerate-view (graph class-name view-name)~ ::
  Force-rebuilds one view's index from scratch (delete + full rescan).  Rarely needed by hand — ~def-view~ rebuilds automatically when its definition changes — but available as the single-view force hammer.

- ~regenerate-all-views (graph)~ ::
  Force-rebuilds every view in the graph.  ~open-graph~ (and ~open-memory-graph~) accept ~:regenerate-views t~ to run this at open time.  Also the views half of an index-backend migration: after reopening with a new ~:index-backend~, this rebuilds every view on the current backend (see Chapter 3).

- ~regenerate-unique-indexes (graph)~ ::
  Drops and rebuilds every ~:unique~ constraint index on the graph's *current* index backend, re-persisting each index's backend tag.  The unique-index half of an in-place skip-list→B+ tree migration (paired with ~regenerate-all-views~ and ~regenerate-spatial-indexes~; see Chapter 3).

**** General ordered indexes (~:index~ / ~def-index~; see Chapter 8)
- ~def-index (owner-class slot graph-name &key canonicalize)~ ::
  Declares an ordered secondary index on ~owner-class.slot~ (spanning subclasses) in ~graph-name~; declarative and idempotent like ~def-view~.  The slot-option form ~(slot :index t | <canonicalizer>)~ is equivalent for a single slot.  ~:canonicalize~ is an optional 1-arg function applied before keying (e.g. ~string-downcase~).
- ~index-lookup (graph class slot value &key (collect-p t))~ ::
  The nodes of ~class~ (and subclasses) whose ~slot~ equals ~value~, via the ordered index (equality).  Resolves nodes in ~graph~.  A declared-but-empty index returns an empty result; an unindexed slot signals an error.
- ~index-range (graph class slot &key start end)~ / ~map-index (function graph class slot &key start end)~ ::
  The nodes whose ~slot~ is in ~[start,end]~ (inclusive; open-ended when ~nil~), in ascending value order — collected, or streamed to ~function~.
- ~regenerate-secondary-indexes (graph)~ ::
  Drops and rebuilds every ordered index on the graph's *current* index backend — the ~:index~/~def-index~ half of an in-place backend migration (paired with ~regenerate-all-views~, ~regenerate-unique-indexes~, ~regenerate-spatial-indexes~; see Chapter 3).

**** Graph Traversal & Mapping
- ~map-vertices (function graph &key vertex-type include-vertex-types exclude-vertex-types include-subclasses-p ... )~ ::
  Applies a Lisp ~function~ to every vertex.  Filter with ~vertex-type~ (a single type) and/or ~include-vertex-types~ (a list); ~exclude-vertex-types~ removes types; unless ~include-subclasses-p~ is NIL (default T) a named type also matches its subtypes.  The fully-untyped scan is a full lhash scan (and reads live versions -- see the function docstring), so avoid it on large graphs without a filter.

- ~map-edges (function graph &key edge-type include-edge-types exclude-edge-types include-subclasses-p vertex direction ... )~ ::
  Applies a ~function~ to every edge.  Filter with ~edge-type~ (single) and/or ~include-edge-types~ (a list), ~exclude-edge-types~, and ~include-subclasses-p~ (default T, so a parent edge type also matches its subtypes -- mirroring ~map-vertices~); or constrain to a ~vertex~ + ~direction~ (:in/:out) or a ~from-vertex~/~to-vertex~ pair.

- ~outgoing-edges (vertex &key edge-type include-edge-types include-subclasses-p)~ ::
  A convenience function that returns a list of a vertex's outgoing edges. ~edge-type~ (single) / ~include-edge-types~ (list) filter by type; subtypes are included unless ~include-subclasses-p~ is NIL.

- ~incoming-edges (vertex &key edge-type include-edge-types include-subclasses-p)~ ::
  As ~outgoing-edges~, for incoming edges.

- ~traverse (vertex &key ... )~ ::
  Performs a breadth-first search traversal starting from a given vertex.

- ~stop-replication (graph)~ ::

**** Spatial (see Chapter 13)

- ~make-point (lon lat)~ / ~make-linestring (coords)~ / ~make-polygon (rings)~ / ~make-multipolygon (polygons)~ ::
  Construct WGS84 ~geometry~ values ((lon lat) order). Accessors: ~geometry-kind~, ~geometry-coordinates~, ~geometry-lon~, ~geometry-lat~, ~geometry-bbox~.

- ~node-geometry (node)~ ::
  Generic function (default ~nil~) returning the geometry a node occupies /and/ the slot it came from, as ~(values geometry slot-name)~. Marking a geometry slot ~:index t~ wires its default up automatically; specialize it explicitly only for a *computed* geometry (such a method reports no slot, and its class is indexed — and scoped — under the most general class carrying the method). Geometry-bearing nodes are then maintained automatically in the spatial index.

- ~(slot :type geometry :index t :spatial-precision N :spatial-max-cells M)~ (slot options) ::
  ~:index t~ opts a geometry slot into spatial indexing; optional
  ~:spatial-precision N~ sets that index's geohash grid precision (default 7);
  optional ~:spatial-max-cells M~ sets that index's max-cells cap (default 16384).

  Graph-wide defaults are set via ~make-graph~'s ~:spatial-precision~ and ~:spatial-max-cells~.


- *scope* (first argument to every query below) ::
  A node-class name, a list of node-class names, or ~:all~. Selects which per-class spatial indexes are scanned /and/ filters the results by type. Signals when it names a class that is not spatially indexed; returns ~nil~ for a class whose index is simply empty.

- ~find-nodes-near (scope lat lon radius &key graph)~ ::
  Live nodes in ~scope~ within ~radius~ metres of ~(lat lon)~, nearest first, as ~(node . distance)~.

- ~find-nearest-k (scope lat lon k &key graph max-radius)~ ::
  The ~k~ nearest live nodes in ~scope~ to ~(lat lon)~, nearest first, as ~(node . distance)~. Bounded by ~max-radius~ (default 25 km); returns fewer than ~k~ if fewer nodes lie within it.

- ~find-nodes-within (scope area &key graph)~ / ~find-nodes-intersecting (scope area &key graph)~ ::
  Live nodes in ~scope~ whose location lies inside — respectively, overlaps — the ~area~ geometry.

- ~(find-near ?node scope lat lon radius)~ / ~(find-nearest ?node scope lat lon k)~ / ~(find-within ?node scope area)~ / ~(find-intersects ?node scope area)~ ::
  Prolog functors that yield matching nodes, composable with the rest of a query.

- ~geohash-neighbor (cell dlon dlat)~ / ~geohash-neighbors (cell)~ ::
  Grid helpers: the cell ~dlon~/~dlat~ steps away (wraps the antimeridian, ~nil~ off a pole), and the 8 same-precision cells surrounding ~cell~.

- ~spatial-indexes (graph)~ / ~spatial-index-for (graph owner-class slot)~ ::
  The per-~(owner-class . slot)~ spatial-index registry, and the one index for a
  given owner class and geometry slot. Per-index introspection:
  ~spatial-index-precision~, ~spatial-index-max-cells~,
  ~spatial-index-precision-counts~, ~spatial-index-coarsest-precision~.

- ~rebuild-spatial-indexes (graph)~ ::
  Rebuild /every/ spatial index from scratch by scanning every live node with a
  ~node-geometry~ and routing it into the ~(owner . slot)~ index its geometry slot
  selects. Adopts the per-class scheme on a graph that predates it, or repairs.
  Run when the graph is quiescent (like ~regenerate-view~). Returns the number of
  nodes indexed.

- ~regenerate-spatial-index (graph owner-class slot)~ ::
  Drop and rebuild /one/ ~(owner . slot)~ index, re-deriving its precision
  histogram from live nodes. The manual recovery for an index whose selectivity a
  single oversized insert degraded — prefer this to rebuilding every index.

- ~regenerate-spatial-indexes (graph)~ ::
  Rebuild every spatial index on the graph's *current* index backend — the
  spatial half of an in-place skip-list→B+ tree migration (paired with
  ~regenerate-all-views~, ~regenerate-unique-indexes~,
  ~regenerate-secondary-indexes~; see Chapter 3).

- ~install-spatial-indexes (graph)~ ::
  Called at open (the mirror of ~install-views~ / ~install-secondary-indexes~):
  rebuilds any spatial index whose /persisted/ precision no longer matches the
  ~:spatial-precision~ its slot option now declares. Creates nothing — indexes are
  still created lazily, at the first geometry-valued write.

- ~audit-spatial-slots (graph)~ ::
  Read-only exhaustive sweep: reports each class carrying more than one
  geometry-valued indexed slot — as ~(class winning-slot . inert-slots)~. The
  counterpart to the write-path inert-slot warning (see "Making a node type
  spatial"); wire it into a schema test suite or run it after a migration.

- ~make-spatial-replication-filter (area)~ ::
  Build a slave-graph ~:replication-filter~ predicate from ~area~ (a ~:polygon~ /
  ~:multipolygon~): the slave applies non-spatial nodes plus spatial nodes inside
  ~area~, so it holds only its area of operations. See "Subset replication" above.

**** Graph Algorithms (optional ~graph-db/algorithms~ add-on)

- ~maximum-flow (source sink &key algorithm edge-type graph)~ ::

- ~generate-graph (model size &key vertex-constructor edge-constructor p saturation-point graph)~ ::
