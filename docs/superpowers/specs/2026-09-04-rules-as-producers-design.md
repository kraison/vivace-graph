# graph-db/rules: rules as versioned producers — design

Issue: #304 (epic). Status: approved in discussion 2026-09-04. Slices
are sub-issues of #304; this document is the record they argue from.

## 1. Purpose

The "derived" half of derived-and-checkable (#109). A rule is a
registered, versioned producer whose claims are derived from other
claims under the same validation every write gets, carry their
premises as provenance, and are regenerated by sweeping the producer.
Everything a rule does is readable from the store afterwards: which
rule, which version, from which premises, refused by which constraint.

Design targets, in order: an operations model in one store whose rules
derive facts such as "subject S is affected by A while it runs V" (the
first consumer, kraison/blackboard#7); then kraison/cl-llm#24,
inference across stores over the agent memory.

## 2. What exists and what is missing

Exists: the claim record with `producer`, `rule-version`, `method`,
`standing` and validity/transaction extents; `claims-by-producer`
(audit) and `delete-claims-by-producer` (regeneration, sweep-then-
insert, design §6.4); commit-time validation of every write (#301);
the guarded Prolog runner (`graph-db/query`, #322); index-backed
generators `find-by-slot`/`find-slot-range` (#102); one snapshot clock
across stores (#94).

Missing: any Prolog view of claims as facts; any way for a rule body
to create a claim (the only `:write` functors retract); provenance;
a rule as a store record; tabling (#122, open).

## 3. Home

New subsystem **`graph-db/rules`**, `:depends-on (:graph-db/spacetime
:graph-db/query)`, pathname `rules/`, package `graph-db.rules`. Core
and spacetime are untouched except where a slice names an export.

## 4. Claims as facts (slice 1, #304-S1)

Global Prolog functors registered by `graph-db/rules`, so the guard's
whitelist admits them by name from any store:

| functor | binds | generates from |
|---|---|---|
| `claim/7` `(?c family ?sns ?skey relation ?ons ?okey)` | a claim node of `family` (parent class name) | the subject index when `?sns ?skey` are bound, else the object index when `?ons ?okey` are bound, else the producer index when combined with `claim-producer/2` in the same body, else refused as cost-unbounded (#285) |
| `claim-current/1` | true when the claim's transaction period is open | filter |
| `claim-valid-at/2` `(?c instant)` | true when the claim's validity extent contains `instant` (an ISO string or a `local-time` timestamp) | filter |
| `claim-producer/2`, `claim-standing/2`, `claim-relation/2`, `claim-rule-version/2` | the slot values | filter, or generator for `claim-producer/2` through the producer index |

Unary claims bind `?ons ?okey` to NIL. Every generator copies
`find-within/3`'s trail discipline (#102). Retracted claims are
generated unless `claim-current/1` filters them, the same default as
`claims-touching`. A family name that is not registered signals
`unknown-claim-family`, which the runner reports as an ill-typed goal.

Usable on its own: kraison/blackboard slice 1's `select` gets claim-
level queries with this slice alone.

## 5. The rule record (slice 2, #304-S2)

`(def-source rule ...)` in `graph-db/rules`, one vertex per rule
version, identity namespace `:rule`, key `name`:

| slot | type | meaning |
|---|---|---|
| `name` | canonical string `[a-z0-9-]+` | the rule; producer is `rule/<name>` |
| `version` | canonical string | `rule-version` on every derived claim |
| `family` | symbol name | the claim family (parent) it derives into |
| `head` | string | one claim pattern, §6 |
| `body` | string | guarded Prolog goals, §6 |
| `extent-policy` | `:premises` (default) or `:none` | §8 |
| `enabled` | boolean | a disabled rule is compiled but not run by `run-rules` |

Facets: identity as above; `:time :none`; `:attribution :none`;
`:sensitivity (:class :internal)`; `:space :none`; `:registration
:none`; `:indexed-text (:text-fn body)` so a rule is searchable.

Writing a rule is an ordinary write in the store it derives into,
validated like any other. Two rules with one name and one version are
a uniqueness violation; a new version is a new record, and the old
version's claims are swept by the next run under §7.

**The Lisp escape hatch.** `(def-rule name (&key version family head
body extent-policy) ...)` builds the same compiled form in the image
without a store record, for engine-internal and operator rules. It is
registered as a producer identically and runs through the same
`run-rule`. A stored rule and a `def-rule` with the same text derive
identical claims (tested, §11).

## 6. Compiling

`compile-rule graph rule` runs the rule's `head` and `body` text
through `graph-db/query`'s screen, reader and whitelist against the
store's schema plus §4's functors, in a scratch package deleted
afterwards, so a rule can name only what a guarded query can name.

- The head is exactly one `claim/7` pattern with `?c` unbound, a bound
  `family` equal to the rule's, a bound relation, and endpoint
  arguments that are literals or body-bound variables. Anything else
  is `rule-compile-error` naming the head.
- The body is one or more goals. Effects are off: a body that names a
  `:write`, `:eval` or `:io` functor is refused by the guard as today.
- **Recursion is refused** until #122: the compiler builds the graph
  from each rule's head relation to the relations its body's `claim/7`
  goals read, over every enabled rule in the store plus the `def-rule`
  registry, and refuses a rule that closes a cycle, naming the cycle.
  A rule that reads its own head relation is the one-node case.
- Compilation runs on `open-graph` for every stored rule (a rule that
  fails to compile is logged and disabled, never refused at open, so a
  store with one bad rule still opens) and on every rule write.

## 7. Running

`(run-rule graph rule) => rule-report`, in one transaction:

1. `delete-claims-by-producer` for `rule/<name>`, both arities, in the
   rule's family and in the `derivation` family (§9).
2. Evaluate the body under `run-query-goals`' rails with effects off,
   one snapshot, the operator's budgets (`*rules-max-inferences*`,
   `*rules-timeout*`, defaults the DSL's), collecting solutions.
3. For each solution, construct the derived claim: the head's
   endpoints and relation, `producer "rule/<name>"`, `rule-version`,
   `standing :inferred`, `method` NIL, extent per §8. Duplicate
   solutions (same identity tuple) collapse to one claim.
4. Write one `derived-from` claim per premise (§9).
5. Commit. Validation runs as for any write; a refusal unwinds the
   whole run — the sweep included, so the previous derivation stands —
   and the report carries the violated families and the rule name.

`(run-rules graph) => list of rule-report`: every enabled rule in
dependency order (a rule that reads relation R runs after the rules
that derive R). Triggering on premise commit is not built here: it is
kraison/blackboard slice 4's subscription mechanism, which will call
`run-rule`.

The report: `rule-name`, `version`, `outcome` (`:derived` or
`:refused`), `derived` count, `swept` count, `refusals` as `(family .
text)` in family order, `inferences`, `elapsed`.

## 8. Validity of a derived claim

For a temporal family, a derived claim's validity extent under
`:extent-policy :premises` (the default) is the **intersection** of
the validity extents of its premises — the claims bound to `?c`
variables in the body's `claim/7` goals for that solution. A premise
with no extent contributes nothing; if no premise has one, the derived
claim has none, which a temporal family then refuses at construction
(`missing-claim-identity-component`), reported as a refusal naming
the rule. An empty intersection means the premises never held at once:
no claim is derived for that solution, and the report counts it under
`disjoint-premises`.

`:extent-policy :none` derives claims with no extent, for
non-temporal families.

`cl-temporal-extent` has `extents-intersect-p` but no intersection
constructor; slice 2 adds `extent-intersection a b => extent or NIL`
there (its own PR, kraison/cl-temporal-extent), with the closed-
interval semantics the substrate uses (S1a: closed, inclusive, UTC).

## 9. Provenance

A claim family `derivation` declared by `graph-db/rules` in every store
that holds rules (`def-claim-classes derivation`, non-temporal): binary
claims `(subject (:claim . <derived identity key>), relation
"derived-from", object (:claim . <premise identity key>))`, producer
`rule/<name>`, `rule-version` the rule's. Identity keys are
`claim-identity-key` strings, so provenance survives the premise's
retraction and regeneration (#303), and `split-claim-identity-key`
(#321) resolves a premise back to its claim.

Reads:

- `(premises-of graph claim) => claims` — the premises a derived claim
  came from, resolved through the subject/producer indexes.
- `(dependents-of graph claim &key current) => claims` — every derived
  claim whose provenance names `claim`, one `claims-touching` on the
  object endpoint. This is what "retracting a premise makes its
  dependents findable" means; nothing is re-derived automatically.

## 10. Cross-store (slice 3, #304-S3)

A rule declared in store A may read stores in a **scope** — a list of
open graphs the operator hands `run-rule`, A first — and writes only
A. `claim/7` generates over every store in scope; a premise from store
B is recorded with its store name in the `derived-from` claim's
`method` slot, the convention cl-llm's evidence claims use. Reads
resolve at one instant under the shared clock (#94). Slice 3 is what
kraison/cl-llm#24 needs.

## 11. Testing

FiveAM system `graph-db/rules-test`, on-disk stores, subprocess only:

- S1: each functor generates the right claims from each index and
  refuses generation with nothing bound; `claim-current/1` and
  `claim-valid-at/2` filter as `claims-touching :current`/`:at` do;
  an unregistered family is ill-typed, not a fault.
- S2: a rule with a version derives claims whose producer and
  `rule-version` identify it; running version 2 after a sweep leaves no
  version 1 claim; a derived claim's provenance names its premises and
  `dependents-of` a retracted premise finds it; a derivation violating
  a declared constraint (a `def-unique` collision, an extent
  disjointness) is refused at commit, the report names the rule, and
  the previous derivation is intact; a recursive rule is refused at
  compile with the cycle named; extent intersection: two premises
  overlapping on [t1,t2] derive a claim valid on exactly [t1,t2], and
  disjoint premises derive nothing; a stored rule and a `def-rule` with
  identical text derive `claim-identity-key`-equal sets; a rule that
  fails to compile leaves the store openable.
- S3: a rule in A over premises in A and B derives into A with the
  premise's store named in provenance; nothing is written to B.
- The GUI and query suites unchanged; CI gains a `rules` lane.

## 12. Out of scope

Tabling and recursive rules (#122; slice 4 follows it); incremental
re-derivation on premise commit (kraison/blackboard#5); a rule editor
in the GUI; rules over vertex slots that are not claims (a body may
read them with the schema functors, but only claims are derived);
negation as failure beyond what the engine's `not/1` already offers.

## 13. Dependencies and findings

- `cl-temporal-extent`: `extent-intersection` (§8).
- `graph-db/query`: the compiler reuses `%read-guarded-forms` and the

  rather than reaching for internals.
- Findings against the engine surfaced while building go to their own
  issues and are listed here when a slice lands.
